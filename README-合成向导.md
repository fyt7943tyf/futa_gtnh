# 合成向导（手机网页版）

在游戏客户端里内嵌一个只读的 HTTP 服务，手机连同一个局域网就能打开一个页面：
搜索任意物品、看它在 NEI 里有哪几种做法、自己挑一种配方、填个数量，
然后拿到一份**扣掉你现有库存之后**的分步合成指导。

```
手机浏览器  ──HTTP──▶  游戏客户端里的网页服务  ──▶  NEI 配方表 + 共享背包/玩家背包
```

---

## 一、怎么用

1. 进游戏（不用进世界，主菜单就行），功能默认已经开着；
2. 按 **P**（或输入 `/futaweb`），聊天栏会给出访问地址，形如
   `http://192.168.1.23:8765/`；
3. 手机连**同一个 Wi-Fi**，用浏览器打开这个地址；
4. 第一次打开时后台正在建配方索引（页面顶上有一条进度），建好就能用；
   之后每次开游戏都是秒开（结果缓存在 `config/futa_gtnh/web_recipes.dat`）。

页面上三步：

| 步骤 | 做什么 |
|---|---|
| **搜** | 输入物品名（支持中文、拼音、`@模组名`），点结果进物品页 |
| **选** | 物品页列出它在 NEI 里的**全部**做法（工作台、GT 机器、匠魂……），点卡片上的按钮挑一条；填上「我要合成 N 个」 |
| **看** | 点「生成合成步骤」：最上面是「需要准备」的原材料清单（需要/已有/还缺），下面是按先后顺序排好的合成步骤；点步骤里的任何一种材料可以就地给它换配方，页面会重新规划 |

### 命令

| 命令 | 作用 |
|---|---|
| `/futaweb` | 看状态，并把访问地址打到聊天栏 |
| `/futaweb start` / `stop` | 手动开关网页服务 |
| `/futaweb rebuild` | 丢掉缓存重建配方索引（换了模组之后用） |

## 二、配置（`config/futa_gtnh.cfg`）

这一组配置**只在客户端生效**（配方数据全部来自 NEI，服务端没有它也不需要）。

| 键 | 默认 | 说明 |
|---|---|---|
| `webRecipeEnable` | `true` | 总开关。关掉之后不开端口、不建索引 |
| `webRecipeAutoStart` | `true` | 客户端启动后自动监听 |
| `webRecipePrebuild` | `true` | 启动后自动建索引；关掉就变成「手机第一次打开页面时再建」 |
| `webRecipePort` | `8765` | 监听端口 |
| `webRecipeBindAddress` | `0.0.0.0` | 绑定地址。`0.0.0.0`=局域网可访问；改成 `127.0.0.1` 就只有本机能访问 |
| `webRecipeToken` | 空 | 访问口令。填了之后必须用带 `?k=口令` 的完整地址打开（按键时给的就是完整地址），之后浏览器会记住这个 Cookie |
| `webRecipeSkipHandlers` | `bq_standard,betterquesting,enhancedlootbags,worldgenloot` | 跳过这些处理器（逗号分隔，匹配处理器**标签**，忽略大小写）。见下面「哪些配方不进索引」 |

### 哪些配方不进索引

有些 NEI「配方」不是合成方法，而是「这东西能从哪来」：战利品袋里能开出什么、任务奖励给什么、
世界生成箱子里的战利品表。它们有两个害处：把一堆东西标成**可合成**（规划就会排出
「从战利品袋里开出 64 个」），而且默认挑配方时它们材料极少、永远排在最前面，把真正的生产链挤掉。

实测这三类各占多少条：

| 标签（处理器） | 条数 | 是什么 |
|---|---|---|
| `bq_standard…\|bq_quest` | 3685 | BetterQuesting 任务奖励 |
| `neicustomdiagram…worldgenloot` | 280 | 世界生成战利品表 |
| `enhancedlootbags` | 52 | 战利品袋能开出什么 |

默认就把这三类剔掉。想再剔别的（例如自动贩卖机 `vendingmachine`），往这个配置里追加标签子串即可；
想一个都不剔就留空。处理器**标签**在客户端日志的「处理器」一节里能看到，
形如 `gt.recipe.canner`（纯 ASCII，不随语言变）。

## 三、它到底做了什么

### 数据来源：NEI，不是硬编码的配方表

配方全部来自 NEI 注册的那些配方处理器（`GuiCraftingRecipe.craftinghandlers`）——
也就是说**玩家在游戏里按 R 能看到什么，网页上就能查到什么**：原版工作台、熔炉，
GT 的每一台机器，匠魂、林业、AE2 等模组自己注册的页面，一个都不少。

### 为什么要先建索引

NEI 的一次查询 = 新建一个处理器实例 + 把它那一整张配方表重新读一遍
（GT 的每张机器配方表都是几千到几万条）。查一个物品还能忍，但
「合成 64 个 XX 一步步怎么做」要沿材料树展开几十上百个节点，每个节点问一次
就是几十秒起步。

所以本功能反过来做：启动后在后台把**全部配方读一遍**，压成一张紧凑的列式表，
之后所有查询只查这张表，一次都不再碰 NEI。
这张表会落盘缓存（`config/futa_gtnh/web_recipes.dat`，gzip 压缩后一两兆），
只要模组列表没变就直接复用 —— 进游戏时日志里会写「索引缓存命中」。

在一套完整的 GTNH 客户端上实测：**226 个配方处理器 / 142190 条配方 / 31268 个物品**，
读取耗时约 0.8 秒（命中缓存时约 0.2 秒）；一次合成规划（含展开、扣库存、排序）
平均十几毫秒。

> **标题界面的配方表是「半份」的。** NEI 只在进入世界之后才注册各模组的配方处理器，
> 停在标题界面时只有十几个原版处理器（约 4.4 万条配方）。所以本功能发现处理器变多时
> 会**自动重建索引**（日志里会写「NEI 处理器数量从 15 变成 226，重建索引」），
> 建好之前页面照样能用，只是搜不到那些还没注册进来的机器配方。

### 合成规划是怎么算的

1. **按需展开**：从目标物品出发，每个物品先挑一条配方
   （你在手机上选过就用你选的），按 `需要数量 ÷ 一次产出` 向上取整算「要做几次」，
   再把材料推进队列。
2. **增量展开**：同一条配方可能被后面更大的需求量再次推到，那时只补做
   「多出来的那几次」—— 否则一个菱形依赖（两个中间产物都要同一种钢板）
   会被算两遍。
3. **扣库存**：共享背包 + 玩家背包里已有的量会从**每一层**扣掉。
   中间产物够就不用做那么多次，原材料够就不缺 —— 「还缺多少」就是这么来的。
   共享背包那份数据是打开网页时按需向服务端要的（`PacketStorageSnapshotRequest`，
   只读、带限流），所以**不需要先打开一次共享终端**。
4. **环路**。GTNH 里大量配方是「反过来也能做」的（锭 ↔ 粉、石头 ↔ 圆石）。
   规划时会先按配方选一遍，再把选出来的配方之间的依赖关系排一次序——
   排不完就说明选中的配方里存在互相依赖，这时会把环里的一种物品改成
   「要你自己准备」并重算，直到步骤能排出确定的先后。
5. **副产物不算进需求**：概率产出的第二第三个物品只显示概率角标，不进材料树 ——
   把它们算进需求会让「还缺多少」变得没法解释。
6. **只有流体输入的配方不算数**：GT 的铸造盆之类在配方表里只有流体、没有物品槽，
   照着它算会得出「铁块凭空产出」这种假步骤，所以那种物品一律当作要自己准备。
7. **产出按 NEI 的规则认**：一条配方的产出不只看「主产物槽」——NEI 的约定是
   「主产物槽为空时，把其它槽位当结果」，GT 的 NEI 处理器大量使用这种形态
   （组装机 5511 条里只有 11 条有主产物槽）。不照这个规则办，页面上会有三分之二的
   配方查不到，而玩家在 NEI 里明明看得到 —— 这正是「藻类农场的组装机配方不见了」
   那个问题的成因。一条配方有好几个产出时，**每个产出都能反查得到**。

### 默认挑哪条配方

只看三件玩家自己能理解的事，都做不到就按 NEI 里的顺序：

- 材料种类少；
- 手头已有的比例高；
- 能在工作台里直接做。

另外两类配方**不会**被自动选中，但玩家可以手动选：

- 「把自己变成自己」的 1:1 转换（电路板 ↔ 编程电路这种），沿着它走必然绕回原点；
- 一个物品材料都没有的配方（见上一条）。

真正「哪条对」是你的事：物品页和计划页里每个节点都能改，改完立刻重算。

### 照着做：进度、可并行步骤、还没定的配方

计划页不只是「一张顺序表」，它是一份能勾的施工清单：

- **现在可以做**：按当前进度放行的那一批步骤。它们之间没有依赖，可以同时开工
  （GT 里几台机器一起跑是常态）。勾掉其中一步，等着它的下一步会自动冒出来 ——
  进度存在浏览器本地，不为一勾跑一趟后端。
- **每一步左边的勾**：做完就打勾，卡片会压暗、产物名划掉，概览里的「已完成 N/M」跟着走。
  右上角有「清零进度」。
- **还没指定配方**：按计划顺序（自顶向下）把「用的是自动挑的配方」的步骤列出来，
  点一下就能换掉。规划替你挑得对不对只有你知道，与其去长表里翻，不如按顺序过一遍。

批次是怎么算的：每一步记着「要等哪些步骤做完」（`needs`，放的是步骤号）和
「属于第几批」（`level`）。一批之内互不依赖，批次号从 1 开始、随依赖递增 ——
`level` 的最大值就是「全并行的话要几轮」。

进度按「目标物品 + 数量」分开存，记的是**配方编号**而不是步骤序号：
改了某个物品的配方之后步骤会重排号，按序号记的话勾会串位。

### 手机上怎么「看」配方

手机没有 hover，而格子里的图标只有三十几像素 —— 光看图经常认不出是哪种板、哪个电路。
所以点一下格子会**就地弹出一条物品信息**（名称、数量、库存、模组）：

- 想看这个物品的配方，再点信息条上的「看它的配方」；
- 也就是**识别一个东西不必付出整屏切换的代价**（原来点格子直接进弹层，看个名字要来回跳）。
- 桌面端两条路都留着：悬停看 `title`，点一下看信息条。

**同类型的配方会合并成一张卡片**：同一个处理器 / 同一台机器的配方合成一组，
组标题上带这类配方的**代表图标**（烧制 = 熔炉、组装机 = 组装机方块 ——
图标来自 NEI 自己的 `GuiRecipeTab.getHandlerInfo(handler).getItemStack()`，
所以和游戏里配方标签栏上那个是同一个）、一共几条，用 `‹ 2 / 80 ›` 左右箭头翻。
铁锭就是典型例子 —— 578 条配方里有 80 条都是熔炉（不同矿石烧出来都是铁锭），
不合并的话第一屏就被熔炉占满了，还看不出「这些其实是同一种做法」。

**物品页和「选择配方」弹层用的是同一套合并**（弹层里 23 条同类型配方曾经也是一条一张卡，
手机上一屏都翻不完）。翻页后再点「选它」，选中的确实是翻到的那一条 ——
这一条有专门的断言，因为「界面上动了但选错了」是看不出来的。

图标存的是**物品键**而不是编号，和缓存一起落盘（编号每个会话会重排，
存编号的话下次开局图标就张冠李戴了）。

### 书签组：把「这一套东西」存下来

清单解决的是「这一次一起算」，但做机器往往是成套的（A 64 个 + B 3 个 + C 1 个），
而且今天算完、明天还要再算一次。所以清单之上有一层**可命名的组**：

- 计划页的清单上方是**组标签**，点一下就切过去，接着算；
- 「＋ 新建组」「重命名」「复制一份」「删除本组」都在旁边；
- 一个组里放多个方块，整组一起规划时**公共的中间产物只做一批**（这是多目标规划的意义）；
- 组存在浏览器本地：`futa_gtnh.groups` = `{version, activeId, groups:[{id,name,items}]}`。

**升级不会丢东西**（这是硬要求）：

- 旧版本只有一份清单（`futa_gtnh.basket`）。第一次打开时它被**迁移**成名为「我的清单」的组；
- 旧键**保留不删**，并持续镜像当前组 —— 所以就算降级回旧版本，读到的还是同一份东西；
- 玩家选的**配方**（`futa_gtnh.choices`）、标过的**原始材料**（`futa_gtnh.raw`）、
  指定的**候选**（`futa_gtnh.alts`）三个键，这个功能**一个字都不碰**。

这条要求有实测：`tools/web-test/groups.js` 会往浏览器里塞一份旧格式的数据、
真正重新加载页面，然后断言「组建出来了、条目一致、旧键还在、choices/raw/alts 原样」。
**「还缺多少」的口径**：这份库存 = **共享存储 + 你身上**（主背包和快捷栏），
**不含**背包、箱子这类容器里的东西 —— 那些要玩家自己走过去开，算进来反而会误导。

刚进世界那几秒，客户端的共享存储快照还没同步到，这段时间里算出来的库存全是 0，
于是所有材料都会被报成「还缺」。页面在这种情况下会顶上一条橙色提示
（「共享存储的库存还没同步完」），**不会**拿一个自己都还不知道的答案去下结论；
同步完成后提示自动消失。
**多候选材料可以直接选**：矿物词典那种「任意一种都行」的格子（「也可以用：A / B / C」），
点那个格子 → 信息条里把候选都列出来 → 点一下就改用那一个（再点一次改回自动）。
选择按「**谁的配方 + 哪一格**」记在浏览器本地，跨会话记住。

「谁的配方」这一段是必须的：同一个物品在不同配方里出现在不同格子，光有坐标分不清是哪一条。
后端还会校验「指定的那个是否真的在这一格的候选里」——配方换了、索引重建之后坐标可能指向
别处，那时**忽略这个选择**比默默按一个不相干的物品算要好。

规划时这一格的材料、以及材料表里那份「还缺多少」，都会跟着换成指定的候选。

**搜索结果是分页拉的**：底部有「加载更多（还有 N 项）」。后端一直支持 `limit` + `offset`，
但前端原来写死了 `limit=40, offset=0`，所以搜出多少都只显示前 40 个。
数量超过一组（64）时会附上「几组零几个」**，比如 `4570（71×64+26）`：
4570 这个数字本身说明不了要腾几格背包、要不要带潜影盒。
原数字保留 —— 判断「我够不够」还是得看它。

**合成顺序和现在可以做都画出完整合成表**：每一步的网格、产出、材料用量都在一张卡里。
材料清单只说明「要多少」，摆法还得看网格 —— 两者互补，缺一个都得来回翻。
（后端为此在步骤里带上了完整配方：网格、材料槽、产出槽。）

**网格里的数字是「做 n 次」的总量，不是 NEI 的每次用量**：这一步要做 2048 次，
那么每个槽要备的就是每次用量 ×2048。只写每次用量（NEI 里那个 ×1、×4）会让玩家
照着备少几百倍。每次用量放在提示和信息条里（「每个配方 ×1，本次做 2048 次」），
两个数都看得到。物品页的配方卡片没有「做几次」的概念，那里仍然是每次用量。

**在「选择配方」弹层里换候选，弹层自己也会立刻变**：弹层是独立的一层，页面重画不会带上它 ——
不额外重画的话，就会出现「胶囊上明明写着 ✓ 用这个，上面的格子却还是旧物品」。

**两个排查时才看得见的坑**（都写进了 `tools/web-test/README.md`）：
页面资源一律 `no-store`（否则改了样式还量到旧值）；只改 hash 不会重新加载文档，
量到的可能全是旧行为 —— 怀疑"没生效"时先真正重载一次。
**流体的量按 mB 算**（显示成 L）：配方里的流体是以「伪物品」出现的（NEI/GT 给每种流体造一个
显示用 ItemStack），它的 stackSize 是 1，真正的用量写在 **GTNH 自己的 NBT 键**上
（`mFluidDisplayAmount`，配套还有 `mFluidMaterialName` 这个流体内部名）。Forge 标准的
FluidStack 解析认不出这套键 —— 认不出就会把「每次 144 L」当成 1，界面写成「共需 64」，
而玩家会去准备 64 个单元。

所以材料行/格子上的流体数字一律带 `L`，并且和仓库里的流体按名字对上（仓库那边流体存在
流体页，身份是流体本身，两边本来是两套身份）。匹配要先精确、再只放行「数量/单位」的前缀 ——
放行任意前缀会把 `Molten Borosilicate Glass **Cell**`（那是真物品）也算成流体。

**流体的量写进配方索引缓存**，所以改动用量的算法必须同时升 `WebRecipeIndex.FILE_VERSION`，
否则读的还是旧索引，改了代码却毫无变化。

**流体的身份是「哪一种流体」，不是「哪个显示物品」**：同一种流体在 GTNH 里往往有好几套显示
物品 —— GT 的 `gregtech:gt.GregTech_FluidDisplay`（有材质的带 `mFluidMaterialName`，
水、岩浆、冷却液这种没有材质的只带 `mFluidDisplayAmount`），和 NEI 自己的
`NotEnoughItems:neiFluidDisplay`（流体写在 damage 上，NBT 里什么都没有）。
它们在玩家眼里是同一个东西（都叫「熔融焊锡」），以前却是**两个不同的物品编号**：
搜索里出现两三条同名条目、配方只在其中一条上，而玩家选的配方是按编号存的 ——
于是「我明明给它选了合成方式，规划还是把它当原料」，页面显示「还缺熔融焊锡」。

现在的规则是 **身份键 = `fluid:显示名`**（两套显示物品唯一共有的身份就是显示名，
两者算出来的字符串实测就是同一个），规整后它们合成一个身份。

**身份重复的条目照样占编号，只是指向正式那条**（`WebStore.ALIAS`）：编号只由「物品目录的
扫描顺序」决定，身份上的重复（同一种流体的另一套显示物品、GT 与 NEI 各造的那个）
占号但指向第一个。反过来，**不能**为了去重就跳过一个条目、不给它编号 ——
一跳号，后面所有编号集体前移，玩家存下来的计划就会指到别的物品上（之前正是这么踩的坑）。

于是搜索里只剩一条；老计划里存的那个重复编号会被**指回正式那条**
（所有接口入口统一过一道 `canonicalId`），而不是落到一个同名的、没有配方的空壳上。
### 书签组：把「这一套东西」存下来

清单解决的是「这一次一起算」，但做机器往往是成套的（A 64 个 + B 3 个 + C 1 个），
而且今天算完、明天还要再算一次。所以清单之上有一层**可命名的组**：

- 计划页的清单上方是**组标签**，点一下就切过去，接着算；
- 「＋ 新建组」「重命名」「复制一份」「删除本组」都在旁边；
- 一个组里放多个方块，整组一起规划时**公共的中间产物只做一批**（这是多目标规划的意义）；
- 组存在浏览器本地：`futa_gtnh.groups` = `{version, activeId, groups:[{id,name,items}]}`。

**升级不会丢东西**（这是硬要求）：

- 旧版本只有一份清单（`futa_gtnh.basket`）。第一次打开时它被**迁移**成名为「我的清单」的组；
- 旧键**保留不删**，并持续镜像当前组 —— 所以就算降级回旧版本，读到的还是同一份东西；
- 玩家选的**配方**（`futa_gtnh.choices`）、标过的**原始材料**（`futa_gtnh.raw`）、
  指定的**候选**（`futa_gtnh.alts`）三个键，这个功能**一个字都不碰**。

这条要求有实测：`tools/web-test/groups.js` 会往浏览器里塞一份旧格式的数据、
真正重新加载页面，然后断言「组建出来了、条目一致、旧键还在、choices/raw/alts 原样」。
**「还缺多少」的口径**：这份库存 = **共享存储 + 你身上**（主背包和快捷栏），
**不含**背包、箱子这类容器里的东西 —— 那些要玩家自己走过去开，算进来反而会误导。

刚进世界那几秒，客户端的共享存储快照还没同步到，这段时间里算出来的库存全是 0，
于是所有材料都会被报成「还缺」。页面在这种情况下会顶上一条橙色提示
（「共享存储的库存还没同步完」），**不会**拿一个自己都还不知道的答案去下结论；
同步完成后提示自动消失。
**多候选材料可以直接选**：矿物词典那种「任意一种都行」的格子（「也可以用：A / B / C」），
点那个格子 → 信息条里把候选都列出来 → 点一下就改用那一个（再点一次改回自动）。
选择按「**谁的配方 + 哪一格**」记在浏览器本地，跨会话记住。

「谁的配方」这一段是必须的：同一个物品在不同配方里出现在不同格子，光有坐标分不清是哪一条。
后端还会校验「指定的那个是否真的在这一格的候选里」——配方换了、索引重建之后坐标可能指向
别处，那时**忽略这个选择**比默默按一个不相干的物品算要好。

规划时这一格的材料、以及材料表里那份「还缺多少」，都会跟着换成指定的候选。

**搜索结果是分页拉的**：底部有「加载更多（还有 N 项）」。后端一直支持 `limit` + `offset`，
但前端原来写死了 `limit=40, offset=0`，所以搜出多少都只显示前 40 个。
数量超过一组（64）时会附上「几组零几个」，比如 `4570（71×64+26）`。
这个换算**到处都是**：步骤标题的「做 N 次 → 产物 ×M」、材料行的「共需 / 还缺」、
格子角标旁边的提示、点格子弹出的信息条 —— 它出现在玩家决定「要不要去腾背包」的每个时刻。
格子角标本身放不下五位数（36 像素），超过一万就写「20.5万」，精确值在提示和信息条里。

### 「需要准备」里为什么是它

一个物品会变成「要你自己准备」，只有这几种原因，页面上每一行都会写明是哪一种
（后端给 `reason` 编码，界面翻成人话）：

| `reason` | 什么意思 |
|---|---|
| `none` | 本来就没有配方（矿石、原木这种），只能去挖 / 去找 |
| `raw` | 你把它勾成了「当作原始材料」 |
| `cycle` | 配方互相绕回自己，规划掐断了这一环（换条配方往往就绕开了） |
| `loop` | 这条配方绕回了它自己，只能自己准备 |
| `depth` | 展开层数到顶了，再往下算步骤会过长 |
| `fluid` | 它的配方没有物品材料（只有流体/能量），物品形态上等于凭空产出 |
| `catalyst` | **非消耗品**（可反复使用），只按一份算 |

### 非消耗品：准备一份就够

GT 里一大类东西是**当工具用**的：可编程电路、各种模具、常驻工具、透镜。它们在配方里
出现，但做完还在你手上。规划要是按普通材料算，就会得到「需要 576 个可编程电路」
「做 512 次螺丝刀」这种荒唐结果，玩家还得一件件去标「当作原始材料」。

所以这类物品**不进合成链**，需要量也**不乘合成次数**，只按「单次配方用量的最大值」算：

| 物品 | 之前 | 现在 |
|---|---|---|
| Programmed Circuit | 需要 576（还有 3 个合成步骤） | 需要 1，不进合成链 |
| Mold (Gear) / Mold (Nuggets) | 需要 512 / 8 | 需要 1 |
| 一次性锻造锤 / 一次性锉 | 4570 / 1344 | **不变** —— 一次性工具是设计上就要消耗的 |

自动判定的范围（保守起见只认确定的那几类）：GT 的可编程电路（`gt.integrated_circuit`）、
GT 的常驻工具（`gt.metatool.01`）、名字里带 Mold / 模具 / Lens / 透镜的。
名字里带「一次性」的一律排除在外。

认错了可以改，两个方向都留了入口：材料行上有「这个其实会消耗，按用量算」，
普通材料行上也有「非消耗品，只备一份」。选择存在浏览器本地。

### 默认不会挑的配方

除了「自产自销」和「没有物品输入」，还有一种**同名变体互换**：另一个 meta 1:1 换成本物品。
数据上它不是自循环（输入是另一个物品 id），但玩家看到的是一句废话 ——
「做 64 次：藻类农场 → 藻类农场」，材料还写着「藻类农场 需要 64」。
GT 的多方块控制器就有这种「换个变体」的配方。判据是「同名 + 每次产出 ≤ 1」，
所以「1 个红蘑菇 → 5 个棕蘑菇」这种真有产出的配方不受影响（两者中文名都叫「蘑菇」）。

**「指定配方」和「当作原始材料」是冲突的**：「当作原始材料」的语义是「别展开它」，
而「指定配方」的语义是「就按这条做」，两者同时存在时前者会赢。所以：

- 你给某个物品选配方时，会**自动摘掉**它的「当作原始材料」（选配方这个动作本身就是
  「我要做它」）；
- 万一还是同时存在（比如你先选配方、后来又勾了原始材料），那一行会明确写出来，
  并给一个「改回按配方合成」的按钮。

**掐断循环依赖时不会动你指定过配方的物品**：「我给它选了配方」是这份计划里最强的
意图表达，掐掉它等于当面把玩家的选择删了。规划会改去掐别的物品；实在没得挑时才会
动它，并在警告里点名。

（这两条都是被玩家问出来的：「我明明已经选择了铝杆的配方，为什么铝杆作为原材料」。）

### 在哪改配方

物品页配方卡上的**每一个材料格子**、计划页里**每一步左侧的产物图标**、
**每条材料行**、以及「需要准备」里的每一行，**都是可以点的** ——
点一下就打开那个物品的配方列表，选完立刻重算（和 NEI 里点材料看配方是一个意思）。
鼠标悬停时格子/图标会亮一圈（手机上没有 hover，点一下就是弹层，里面写着名称和库存）。

悬停的提示挂在**整格**上，不在右下角那个数量角标上 —— 角标只有十几像素、
还带 `pointer-events:none`，指针根本停不上去，挂在那儿等于「鼠标放上去什么都没有」。
这一点被玩家抓到过一次：数量为 1 的格子有提示（提示在格子上），
数量大于 1 的反而没有（提示跑到角标上去了）。现在断言里专门盯这条。

手动指定过的物品会带一个**「已选配方」标记**：图标右下角一个勾（网格格子是左上角，
右下角留给数量），旁边再补一个文字标签。这样过一遍长计划时，一眼能看出哪几步用的是
你自己挑的配方，而当前这一步用的到底是不是它，靠配方编号对号判断 —— 手动选了配方、
规划却因为循环依赖绕开了它，标识就不会出现，不会骗你。

## 四、接口（想自己接一个前端时看）

所有接口都是 `GET`，返回 UTF-8 JSON。图标是 PNG。

| 接口 | 说明 |
|---|---|
| `/api/status` | 服务与索引状态（`building`/`progress`/`phase`/`recipes`/`items`） |
| `/api/search?q=&limit=40&offset=0` | 搜物品，返回 `{id,name,mod,stock,craftable,icon}` |
| `/api/item?id=` | 某个物品的全部配方 + 用途。**最多回 80 条**，真实条数在 `recipeTotal` 里（回收类物品的候选配方上万条，全回手机打不开） |
| `/api/plan?id=&count=&stock=1&choices=&raw=` | 合成规划。`choices` 形如 `42:123,77:456`（物品 42 用 123 号配方）；`raw` 形如 `9,15`（这些物品当作自己准备的材料，不再展开）；`catalyst` / `consumable` 用来增删「非消耗品」判定（见下） |
| `/api/icon/<id>.png` | 物品图标 |

配方对象里的 `inputs`/`outputs`/`extras` 是按 `x`/`y` 格坐标摆的槽位，
`alts` 是「任意一种都行」的候选（矿物词典替代品），`chance` 是百分数。

规划结果里每个 `step` 还带：

| 字段 | 含义 |
|---|---|
| `n` | 步骤号（1 开始），和界面上显示的序号一致 |
| `rid` | 这条步骤用的配方编号，`choices` 里填的就是它 |
| `needs` | 要等哪些步骤先做完（**步骤号**，不是内部编号）。空表示原材料齐了就能开工 |
| `level` | 第几批：1 = 一开始就能做。同批之间没有依赖，可以并行 |

## 五、常见问题

**手机打不开页面**

- 确认手机和电脑在同一个局域网（不是手机流量、也不是访客 Wi-Fi）；
- Windows 防火墙可能拦了 `javaw.exe` 的入站连接，放行一次即可；
- 端口被别的程序占了：换 `webRecipePort`，或看日志里
  「网页配方：启动 HTTP 服务失败」那行；
- **同时开了两个客户端**时，只有先起来的那个能拿到端口。后起来的会每 30 秒重试一次
  （日志里是「网页配方：网页服务还没起来，第 N 次重试」），先起来的一关，
  另一个就会自己把页面补上，不用重开游戏；
- 想看地址就在游戏里按 P，聊天栏里给的是**本机网卡的真实 IP**，
  有多张网卡（虚拟机、VPN）时会全部列出来，挑手机能通的那个。

**图标是离屏渲染出来的，不是「读贴图」那条退路**

退路是**静默**的：图标照样显示，只是变回平面贴图，光看图根本分不出来。
所以接口会带一个响应头 `X-Icon-Source: render|texture`，
自测脚本断言它必须是 `render` —— 实测「离屏渲染每次都抛异常」就是这么躲过检查的
（`BufferUtils.createFloatBuffer` 给的是直接缓冲，`array()` 直接抛，
渲染每次失败、每次悄悄退回，GL 错误还正好是 0，因为压根没画）。

**每次开游戏都在「建立索引」，缓存好像没生效**

先看日志：写「索引缓存命中」就是生效了；写「缓存文件读不出来」说明那份缓存不完整
（写到一半关游戏/崩溃），会自动重建，不影响使用。

**手头有多少东西会不会影响计划**

会，这是默认行为：背包里够了的材料就不用做，计划短、贴近当下。
想提前备料、或者给别人列清单时，点计划页右上角的「按库存算 / 从零算」切过去 ——
那时会把总需求全列出来，不看你现在有什么。

## ⚠️ 已知问题：物品编号仍可能变化

存档里的「手动指定配方」「当作原始材料」「非消耗品标记」「施工进度」都是按**物品编号**
记的，而编号是「物品目录里第几个被登记的物品」。

**身份规整已经不会再动编号了**（v1.27.2 起）：身份重复的条目照样占号、只是指向正式那条，
所以「把 NEI 的流体伪物品和 GT 的流体显示物品并成同一个身份」这类改动，
不会再让它后面的编号集体前移（之前正是这一条把玩家存的计划指到了别的物品上）。

**剩下会动编号的是这两件事**：

- 模组列表变了 —— 缓存按模组列表判定有效性，失效就重建索引；
- 配方里出现、但不在物品清单里的物品（机器产出的中间产物等）按**处理器顺序**补登记，
  而处理器数量随「停在标题界面还是进过世界」而变：

| 状态 | 处理器 | 物品目录 |
|---|---|---|
| 停在标题界面 | 226 | 31268 |
| 进过世界之后 | 366 | 64932 |

实测同一台机器上「藻类农场」的编号从 **18919 变成了 35975** ——
也就是说**换一次索引状态，之前保存的选择可能落到别的物品上**。

正确的修法是把这些状态改成按**物品键**保存（`registryName@meta` 或 `fluid:显示名`，
后端已有 `WebStore.idOfKey`），用的时候再解析成当前编号。在那之前，如果发现选择对不上，
把那一项删掉重新加一次即可。

**配方编号（`rid`）从 v1.27.3 起是稳定编号**，由配方内容算出（处理器标签 + 耗电耗时 +
每格物品的稳定键/数量/坐标/概率），不再是「这次索引里的第几条」。以前它一变，
你选的配方就悄悄滑到同名的另一条上（实测：给熔融焊锡选的提取机配方滑成了另一条回收配方，
规划于是绕回自己报缺料）。现在重建索引、换模组版本都不影响它。
如果你选的配方**真的**找不到了，规划会明确点名（「这几样你之前选过配方，但当前索引里找不到那一条」），
不会再一声不响地换一条。

缓存写在 `config/futa_gtnh/web_recipes.dat`，采用「先写 `.tmp` 再原子替换」，
所以中途被杀掉的只会是临时文件，不会把上一份好的覆盖掉。

缓存里每个条目存**两份键**（v13 起）：`注册名@meta` 用来把条目找回来，
身份键（流体的形如 `fluid:显示名`）用来认身份。以前只存身份键，于是
「`fluid:Kanthal` 反推不出是哪个物品」—— 回读缓存时整批流体条目被静默丢掉，
表现是「重启之后所有流体都没有配方了」，而日志里一个字都没有。
回读时找不回来的条目数现在会打出来（`缓存里有 N 个条目在当前客户端上找不到`）。

缓存**只按模组列表判定有效性**（id + 版本），不看「此刻 NEI 注册了多少个处理器」——
处理器是 NEI 按需注册的，进世界之前只有十几个，用它当判据会让缓存永远命不中。
配套地，索引只在**处理器变多**时重建：从缓存里读出来的那份可能是上次进世界时建的
（两百多个处理器），比此刻的十几个更完整，重建反而会把它换差。
改了 NEI 自己的配置（`config/NEI/handlers.patch` 之类）想让缓存失效时，
用 `/futaweb rebuild`。

**页面说「配方索引还在建立」**

第一次开页面确实要等：处理器有好几百个，配方十几万条。页面顶部有进度。
等它跑完会写进 `config/futa_gtnh/web_recipes.dat`，下次开游戏就秒开了。
不想每次启动都建，把 `webRecipePrebuild` 关掉即可。

**有些物品没有图标 / 图标和游戏里不一样**

正常情况下图标是**离屏渲染**出来的 —— 也就是「游戏怎么画，我就怎么画」：
3D 方块模型、GT 材质类物品的着色（灰白底图乘材质颜色才是你看到的棕色木板）、
流体显示那种运行时绘制的物品，全都自动一致。

按 4 倍光栅化后再裁掉空白边，所以手机上（槽位 36 CSS 像素、DPR 2~3）
机器方块的散热口、锭子的棱面这些细节都还在，不是放大出来的糊块。

渲染不可用时（还没进游戏、游戏窗口最小化导致不渲染、超时）会退回「读资源包贴图」：
那条路不完美 —— 方块是平的、材质没上色 —— 但不会白屏。
持续空白的话刷新一次页面即可（超时不会被记成「这个物品没有图标」，下次还会重试）。

**配方里显示的物品和游戏里看到的不是同一个**

物品身份按「物品 + 元数据」算，**不看 NBT**。这是刻意的：配方树要连得起来。
代价是极少数靠 NBT 区分的输出（附魔书之类）会合并成一个节点。

**「用于」那一栏是空的**

这一栏（这个物品能拿去做成什么）还没做，接口留了字段但暂时返回空数组。

**步骤里的「还要准备」里出现了很奇怪的东西**

那些是 NEI 的「其它槽位」（燃料、模具之类），本功能只把它们列出来，不参与材料树展开。
燃料槽在 NEI 里是「一堆可选的燃料循环显示」，页面显示的是其中一种，换个配方做就行了。

**和服务端版本不一致时**

新增了一个客户端 → 服务端的只读请求包（共享背包快照）。老服务端收到会直接忽略它，
表现就是「共享背包那部分库存算不进去」，玩家背包和配方功能都照常 —— 不影响游戏。

## 六、实现位置

```
src/main/java/com/futa_gtnh/web/
├─ WebRecipeService.java   生命周期、按键/命令、每 tick 推进
├─ WebRecipeServer.java    HTTP 路由与 JSON 输出
├─ WebRecipeIndex.java     全量配方索引（列式存储 + 落盘缓存）
├─ WebPlanner.java         合成规划（数量、配方选择、库存扣减、破环、拓扑排序）
├─ WebStore.java           物品目录、搜索、库存快照
├─ WebIconRenderer.java    物品图标的离屏渲染（和游戏里长得一样）
├─ WebIcons.java           图标入口：离屏渲染 + 读贴图兜底、缓存
├─ WebClientTasks.java     把「必须在客户端主线程做的事」搬过去
└─ WebJson.java            极简 JSON 输出器

src/main/resources/assets/futa_gtnh/web/
├─ index.html   页面骨架
├─ app.css      手机优先的深色样式
└─ app.js       路由、接口层与渲染（原生 JS，无外部依赖）
```

客户端与服务端的兼容性：除了上面说的快照请求包，本功能不在服务端做任何事
（不开端口、不读配置、不注册包处理器以外的逻辑）。

## 七、自测脚本

改完后端想快速确认没把接口或规划改坏：

```bash
node tools/web-test/smoke.js     # 接口契约（38 项）
node tools/web-test/fuzz.js      # 沿物品目录抽样，检查规划结果的结构不变量
node tools/web-test/ui.js        # 页面交互：无头 Edge 真的去点（需要 Node 22+）
```

前两个只用 Node 自带的 `fetch`，跑的时候游戏要开着。第三个会启动一个独立的无头
Edge 实例（自己的 `--user-data-dir`，不碰你正在用的浏览器），真的去点按钮：
选中一条配方 → 看计划页上有没有标识和图标 → 悬停 → 点图标开弹层 → 清空选择看标识消失。
**静态截图证明不了「点了会怎样」，所以涉及交互的改动要跑这个。**
详见 [tools/web-test/README.md](tools/web-test/README.md)。

页面本身的改动（CSS/JS）它们看不出来，建议顺手用无头浏览器截一张：

```bash
msedge --headless=new --disable-gpu --window-size=400,1520 \
  --screenshot=shot.png "http://127.0.0.1:8765/#/item/3142"
```

**注意 `--window-size` 在无头模式下不一定真的改掉布局视口**（实测 390 宽的窗口里
页面仍按 800 宽排版，结果右边被裁掉、看着像「横向溢出」）。要验手机布局，
用一个 `width:390px` 的 iframe 把页面套起来再截图才是准的：

```html
<iframe src="http://127.0.0.1:8765/#/item/3142"
        style="width:390px;height:1500px;border:0"></iframe>
```
