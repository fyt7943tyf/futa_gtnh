# 全服共享背包（FutaGTNH）

一个 **Minecraft 1.7.10 / GTNH** 附属模组：给服务器加一个**全服所有人共用**的无限存储池，
物品和流体都能放，支持搜索，并且能和每个人的个人背包双向交换。

---

## 它解决了什么问题

GTNH 到中后期，仓库管理会变成主要负担：几十个箱子、抽屉、储物总线，
找一样东西要翻半天；多人服务器上「谁把铂锭拿走了」永远说不清。

这个模组把「存储」从**空间问题**变成**列表问题**：

- 全服一个池子，所有维度共用，不存在「东西放在哪个箱子」；
- 单条目上限是 `long`（约 9.22 × 10¹⁸），实际等于无限，不用再操心堆叠；
- 支持搜索、排序、分页，几千种物品也能秒找；
- 流体和物品同等对待；
- 方块终端还能当 GT 管道/泵的接口，流体和物品都能直接对接自动化。

---

## 怎么拿到 / 怎么打开

### 1. 合成「共享终端」方块

```
玻璃      末影珍珠   玻璃
末影珍珠   箱子      末影珍珠
玻璃      末影珍珠   玻璃
```

用的是矿物词典（`blockGlass` / `enderpearl` / `chestWood`），
所以装了别的模组、这些材料被统一成别的物品时配方依然成立。

放下来**右键**即可打开界面。潜行右键会放行给其他工具（比如 GT 扳手），
所以扳手调朝向之类的操作不会被界面抢走。

### 2. 按键随时随地打开

默认按键是 **B**（在「选项 → 控制」里可以改，分类是 `FutaGTNH`）。

服务端可以在配置里关掉这个功能（见下面的「配置」一节），
关掉后就只能跑到方块终端前面才能访问。

界面比常规容器宽（232 而不是 176），**只加宽不加高** —— GUI scale 4 时竖向只有

### 物品页签

| 操作 | 效果 |
| --- | --- |
| 左键 | 取 1 个 |
| 右键 | 取半叠 |
| Shift + 左键 | 取一整叠（数量由配置 `shiftClickWithdrawAmount` 决定，默认 64） |
| Shift + 右键 | 尽量塞满背包 |
| 中键 | 取一整叠 |
| 光标拿着东西时左键 | 把光标那一叠存进去 |
| 光标拿着东西时右键 | 从光标那一叠存 1 个 |
| **Shift + 左键点自己背包里的格子** | 把那一格存进去 |
| **Shift + 双击自己背包里的格子** | 把背包里所有**同种**物品一次全存进去 |
| 滚轮（鼠标在网格上） | 翻页 |
| PageUp / PageDown | 翻页 |

> **滚轮只翻页，任何时候都不会取出物品。** 整合包里有**两个**模组都会做「滚轮滚过格子就把
> 物品在两边搬一次」：**NEI** 的「滚轮转移物品」（`config/NEI/client.cfg` 的
> `disableMouseScrollTransfer`，默认开着）和 **MouseTweaks** 的滚轮 tweak
> （`B:WheelTweak`，装了 NEI 时它会主动让位）。它们的做法都是**替玩家合成一次槽位点击**，
> 落到共享存储上就变成「滚一格掉出来一个物品」。本模组把两侧都关在了终端界面之外：
> NEI 那边把界面登记进 `GuiInfo.customSlotGuis`，MouseTweaks 那边实现
> `IMTModGuiContainer` 并让 `isWheelTweakDisabled()` 返回 true。
> 详见下面「为什么滚轮以前会掏出物品」。

> **[全部] / [快捷栏] 会跳过你当前手持的那一格** —— 一键倒空背包太容易手滑，
> 而「工具留在手上」是最不容易出事的默认值。真想把正拿着的东西也存进去，
> 单独 Shift 点那一格即可。

### 「拾取自动入库」开关

页签那一行的右边有一个按钮：**自动入库 开 / 关**。悬停能看到说明。

**打开之后，你捡到的所有东西都直接进共享背包，根本不进你自己的背包** ——
包括挖矿掉落、怪物掉落、别人丢给你的。

这是**每个玩家各自**的开关，别人开了不影响你；状态存在你的人物数据里，
**下线再上、甚至死一次都还在**。

两个实现上的细节值得知道：

- **背包满了也照样入库。** 拦截点选在 `EntityItemPickupEvent`，它在原版
  `EntityItem.onCollideWithPlayer` 里、调用 `addItemStackToInventory` **之前**触发，
  取消之后整个拾取流程直接返回。如果反过来做（先让原版捡进背包再搬走），
  背包一满原版就捡不起来，连事件都不会有 —— 而这个功能要的恰恰是
  「我背包里什么都不想留」。
- **不会和别的玩家抢。** 处理完一个掉落物会先把它标记为已消失，
  同一 tick 内另一个玩家的同名事件会因此在入口处直接返回，
  不会出现两个人都把同一份东西存进仓库。

> 从终端**取**东西不受这个开关影响 —— 取出来的东西不会立刻又被收回去。
> 取用走的是直接写背包，不经过拾取事件。

### 装备栏和合成栏（右侧侧栏）

终端界面右侧有**你自己的装备栏**和**一个 3×3 合成栏（含产物格）**，
所以这个界面实际上是你背包的超集（比原版背包多一整排合成格）：

| 操作 | 效果 |
| --- | --- |
| **Shift + 左键点某个护甲槽** | 把身上穿的那件装备存进共享存储 |
| **Shift + 左键点合成栏某一格** | 把那一格的材料存进共享存储 |
| 合成栏里摆好材料 → 左键产物格 | 正常合成（和背包界面完全一样） |
| **Shift + 左键点产物格** | 连续合成，直到材料用完或背包放不下 |
| 关掉界面 | 合成栏里的东西**自动退回背包**，实在放不下才掉地上 |

两个刻意的设计：

- **[全部] / [快捷栏] / [主背包] 不会顺手套走你身上穿的装备。** 护甲只有在
  你明确 Shift 点击那个护甲槽时才会被存进来 —— 一键把角色扒光显然不是好默认值。
- **产物放不下就干脆不合成。** 原版 `ContainerPlayer` 在这里有个丢东西的口子：
  只要背包能塞下产物的*一部分*，它就会把整份材料扣掉，没塞进去的那部分产物
  随后被重算成「合成栏已空 → 没有产物」而蒸发。这个终端里不会发生这种事，
  你看到的只会是「背包满了」。

> **顺带一提**：原版背包界面在关闭时会把 2×2 合成栏里的东西**直接丢到地上**
> （这是 1.7.10 的 `ContainerPlayer.onContainerClosed` 的行为，开任何箱子都一样）。
> 这个终端做得比原版好一点 —— 关界面时先把东西退回背包，放不下才丢。
>
> 合成栏是 **3×3**（不是原版背包那个 2×2），所以工作台那一类配方可以直接在这里摆。
> 2×2 的配方当然也能做：原版 `ShapedRecipes.matches` 本来就会在整个 3×3 里平移匹配。
>
> 侧栏只有 53px 宽（x=178..230），3×3 需要 54px，所以合成栏从 x=177 起画 ——
> 正好压掉分隔线旁边那条 1px 高光，格子自己的浅色边框顶上去。
> 界面**没有变高**（还是 232×252）：GUI scale 4 时竖向只剩 270px，再高就有玩家
> 看不到底部了，所以 3×3 是靠把箭头和产物格往下挪 18px 腾出来的。

#### 合成栏可以直接从共享存储取料（NEI 联动）

装了 NEI 时，对着终端界面里的物品按 R/U 查配方，配方界面里会出现**「填入合成栏」**
按钮（和原版背包界面那个一样）。区别在于：**材料不够时直接从共享存储补**，
不需要先取到背包里。

- 「材料够不够」的绿红提示把**背包 + 共享存储**算在一起 —— 仓库里有就算够；
- Shift 点按钮 = 尽量多填（每格填到堆叠上限），普通点 = 只填一次的量；
- NEI 的**自动合成**按钮也可用：服务端循环「填栏 → 取产物进背包 → 补材料」，
  直到合成次数用完、材料用尽或背包放不下。

**实现要点**（为什么不像 NEI 默认那样模拟点击）：NEI 默认的转移靠
`FastTransferManager` 模拟一串窗口点击、只认玩家背包；要让材料来自共享存储，
就得把取料和点击排进同一个时序，网络上没有这个保证。所以本模组把布局
（每格的候选物品 + 用量，候选就是 NEI 给出的矿辞置换组）打包发给服务端
（`exchange/CraftFiller.java`），服务端**直接填容器自己的合成栏**：
材料优先从背包取、不足从存储取，全程服务端权威、数量守恒，
`detectAndSendChanges` 负责同步回客户端 —— 原子、无竞态、无本地预测。
自动合成走的是和 Shift 点产物格**同一条**取出路径（含防产物蒸发的容量检查）。

> 合成栏是 3×3，所以工作台配方（3×3）和原版背包那种 2×2 配方都会出现填充按钮；
> 只有行列超过三档的配方（某些 GT 多方块结构）不参与，免得摆出个错的形状。
>
> 服务端视角的防刷约束：候选必须是背包/存储里**真实存在**的条目（精确键匹配），
> 数量按实际存量封顶，倍率夹在 64 以内 —— 客户端伪造的包最多「找不到材料」，
> 变不出任何东西。

### 匠魂的工作站：自动从共享存储补料

开着匠魂的工作站界面时，缺的部件 / 材料会自动从共享存储补上（配置项 `tinkersAutoFill`，
默认开；**服务端行为**，各端读服务端那份配置）。覆盖四个地方：

| 工作站 | 自动做什么 |
| --- | --- |
| **工匠工作站 / 工匠锻造台** | 槽里已经有部件、能唯一确定你要造什么工具时，缺的部件（头 / 柄 / 附件，锻造台还多一个「额外」槽）自动补进来，工具当场就出来了 |
| **部件加工台** | 放上图纸后材料自动补 —— 图纸就是意图，缺的只是「用哪种材料」 |
| **合成站** | 记住你摆好的 3×3，合成消耗掉的部分自动补回原样，材料不用自己一趟趟搬 |
| **冶炼炉** | 记住放进去的待熔物，熔掉多少补回多少，界面开着就一直有料 |

**材质按你定的规则挑**：优先和**你已经放进去的那个部件同材质**（比较
`ToolBuilder.getMaterialID`），一个都没放（或那种材质仓库里没有）时退回「共享存储里
**存量最多**的合格材料」。取料永远**玩家背包优先、其次共享存储**，走的是和别处同一条
守恒路径（`SharedStorage.extractItem`），不会凭空变东西。

**为什么「工作站里什么都没放」时不补**：匠魂的工作站是**由部件反推工具类型**的 ——
GUI 左边那排工具类型按钮只影响图标和说明，**根本不发给服务端**
（`ToolStationGui.selectedButton` 纯客户端，`ToolGuiElement` 里也只有图标和文字）。
也就是说工作站本身没有「我要做镐子」这个信号；一个部件都没放时补料就是在替你猜工具类型，
而匠魂的部件是讲材质的，猜错会把好材料白白吃掉。所以规则是：
**放一个能唯一确定配方的部件（比如镐头）进去，剩下的它自己补**；
只放了一根工具手柄（几乎所有工具配方都成立）这种有歧义的情况同样不动。

**实现上最省事的一点**：匠魂把「往槽里放东西」当成合成触发器 ——
`ToolStationLogic.setInventorySlotContents` 里直接调 `buildTool`，
`PartBuilderLogic` 里调 `buildTopPart / buildBottomPart`；合成站与冶炼炉则是
「点产物 / 慢慢熔掉」。所以我们只要把缺的材料写进它的库存，**它自己就把东西做出来了**：
不用改匠魂的代码，也不用模拟点击（模拟点击那套在网络时序上不牢靠，理由见上面 NEI 那节）。
判定和取料全在服务端（`com.futa_gtnh.tinkers` 包），界面开着的每个 tick 跑一次，
关掉界面立刻停 —— 免得变成一个无人看管的自动吞料机。

**已知不做的**：

- 工作站里一个部件都没放时不补（原因见上）；
- **不替你补「强化」（modifier）材料**：那套配方（工具 + 2~3 个强化材料）牵扯的材料价值太高，
  我们只在你能凑出一套合法工具配方时才动手；
- 冶炼炉只在**你开着界面**时补料：关了界面它照样在熔，但我们不继续往里加料；
- 匠魂没装、或版本对不上时整个功能静默失效（启动日志里会有一行「匠魂工作站自动补料已启用」，
  没有这行就是没起来）。

### 流体页签

| 操作 | 效果 |
| --- | --- |
| 左键 | 灌装背包里的容器（默认 1000 mB，1 L = 1 mB） |
| Shift + 左键 | 尽量多灌（整叠空桶会一路灌下去，直到流体不够或背包放不下） |
| 右键 | 取 GT 的**流体显示物品**（数量存在 NBT 里，可以远超 1000 mB） |
| Shift + 右键 | 取尽量多的流体显示物品 |
| 中键 | 把这个流体设为**方块终端的输出**（只有从方块打开时可用） |
| **光标上举着装流体的容器时点一下** | **把容器里的流体倒进共享存储**，倒空后的容器留在光标上 |

> **最后一条是关键**：你举着一桶牛奶、在流体页签里点一下，是「把牛奶倒进去」，
> 而不是「把整个桶当成物品收走」。同一个牛奶桶在**物品页签**里就只是个物品，
> 点一下就是当物品存 —— 该倒料还是该当物品，由你正在看哪一栏决定。
>
> 倒空之后光标上剩下一个空桶；再点一下就会把这个空桶当物品存进去
> （因为这时它已经没有流体可倒了）。
>
> 注意这个动作是**按整叠结算**的：光标上是 16 个牛奶桶就一次倒出 16 桶的量，
> 换成 16 个空桶，不会只入账一桶然后抹掉其余的。

> **流体显示物品是整叠存入的。** 它没有覆写堆叠上限，所以原版会把同流体的显示物品
> 合并成一叠（最多 64 个）；而它的数量信息整体存在 NBT 里，没法「扣一半」。
> 因此存的时候要么整叠收下、要么完全不动 —— 不存在部分存入。
> 取出时一个显示物品承载 `fluidClickAmount` 那么多流体，想要更多就多点几次。

流体的三条取出路径都支持：

1. **灌装容器** —— 通过 Forge 标准的 `IFluidContainerItem` 和
   `FluidContainerRegistry` 两条接口依次尝试。桶、GT 单元、以及其他模组注册过的容器都能用；
   支持部分灌装（把 300 mB 灌进 1000 mB 容量的单元）。
2. **取 GT 流体显示物品** —— 就是 NEI 里看到的那个流体条目。
   数量以 NBT `long` 存储，没有 1000 mB 的上限。
3. **对接相邻的 GT 流体罐 / 管道** —— 见下面「自动化对接」。

### 搜索语法

故意做成 NEI 那一套，GTNH 玩家不用重新学：

| 写法 | 匹配 |
| --- | --- |
| `铁锭` | 显示名（不区分大小写） |
| `tieding` | **全拼**（拼音，见下） |
| `td` | **首字母**（拼音，见下） |
| `@gregtech` | 模组 id 或模组名 |
| `*ingotIron` | 矿物词典名 |
| `#tooltip内容` | 物品 tooltip |
| `铁 板` | 空格分隔 = **与** |
| `铁|铜` | 竖线分隔 = **或** |

> 高级搜索（`*` 和 `#`）是懒加载的：只有你真的用了那个前缀，才会去算矿辞和 tooltip，
> 之后缓存住。几千个条目下这能避免每次敲键都卡一下。

### 用拼音搜中文名

**直接打中文也可以。** GTNH 2.8+ 带的 **lwjgl3ify**（LWJGL3 / 新 Java 环境）自带输入法支持：
它给原版 `GuiTextField` 打了补丁，搜索框一聚焦就激活系统输入法，提交的中文
由它注入输入框。本模组的两个搜索框用的都是原版 `GuiTextField`，
所以**在带 lwjgl3ify 的 GTNH 里中文是直接打得出来的**，什么都不用额外装。

> 环境探测与回退：代码里按「lwjgl3ify 的 `TextFieldHandler` 类在不在」区分环境
> （`client/ImeCompat.java`）。老版本 lwjgl3ify（GLFW 时代，没有这套机制）或纯
> LWJGL2 环境下，自动退回旧的「>255 字符注入」路径 —— 配合 InputFix 一类模组
> 同样能输入中文。两条路径互斥，不会重复插入。

**拼音搜索依旧可用**（不想切输入法的时候更快），全拼和首字母都认：

| 你想找 | 可以敲 |
| --- | --- |
| 铁锭 | `tieding`、`td`、`tie ding` |
| 铁矿石 | `tiekuangshi`、`tks`、`kuang` |
| 锰锭 | `mengding`、`md` |
| 女巫之角 | `nv...`、`nu...`（ü 的两种写法都认） |

多音字取最常用的那个读音（比如「行」按 `xing`）。中文直接粘进去也能用 ——
`Ctrl+V` 粘贴是原版输入框自带的，剪贴板里的中文可以正常进到搜索框里。

> **搜索框要点了才进入输入状态。** 刚打开界面时它**不是**焦点，此时键盘是
> 正常操作（`E` 关界面、`1`~`9` 换快捷栏、`Q` 丢弃……）。点一下搜索框
> 才进入输入状态，这时边框会描一圈绿线；点界面别处就退出来。
>
> 以前是反过来的：搜索框常驻焦点、点了别处也抢回来，理由是「怕敲字母触发
> 快捷键把界面关掉」。那个担心其实不成立 —— 打开共享背包的 `B` 键在
> `KeyHandler` 里有 `currentScreen != null` 的守卫，不可能关掉界面；
> 而原版只对「打开背包」那个键关界面。代价却是 `E` 永远关不掉终端、
> 也没法退出输入状态，所以改成了现在这样。

> 实现上，自研方案的每个条目的搜索文本在**建立索引时**就把拼音算好挂上去，
> 敲键时只是普通的子串匹配，不会因为多挂了拼音而变慢。
>
> **装了 NotEnoughCharacters（NEChar）时拼音匹配整个交给它**（`client/NecharBridge.java`）：
> 拼音全拼/首字母、模糊音（zh→z、ang→an……）、GTNH 生僻字（钅卢这类）、
> 电压名特搜（zpm/max/luv…）全是现成的，而且跟随玩家自己的 NEChar 配置 ——
> 不重复造轮子。没装 NEChar 时用自研拼音表，行为和以前一致。
>
> 自研拼音表两万六千多条，覆盖 GB2312 全部汉字加大量生僻字 —— 特意没有只收常用字，
> 因为 GTNH 的物品名里一堆化学元素名（铱、锇、铪、钌……）恰恰不在常用字表里。
> 第一次用到时才加载，约 10 ms，没打开过搜索界面就完全不会被碰上。
> 数据来自 [mozillazg/pinyin-data](https://github.com/mozillazg/pinyin-data)
> （MIT 许可，上游是 Unicode 联盟的 Unihan 数据库）。生成脚本在
> `tools/pinyin/GenPinyin.java`，生成的拼音表已提交到
> `src/main/resources/assets/futa_gtnh/pinyin.txt` ——
> **日常构建不需要联网，也不需要跑那个脚本**。
> 改过拼音表之后可以用 `tools/pinyin/PinyinCheck.java` 核对几个已知词
> （里面挑了铱、锇、钨这类化学元素名，专门用来抓「只收常用字」这种坑）。

> 另外，两个界面的 `handleKeyboardInput` 都做了处理：1.7.10 只在
> `Keyboard.getEventKeyState()` 为真时才把字符转给 `keyTyped`，
> 而输入法/文本注入类模组送来的事件往往是「只有字符、没有按键」，
> 会被原版直接丢掉。本模组把 `> 255` 的这类字符补转给输入框，
> 所以**如果**你装了 InputFix 一类的模组，中文是能直接打进来的。

### 排序

点右下角的按钮在 **名称 / 数量 / 模组** 之间循环。
「按数量」可以一眼看出自己攒了什么，「按模组」适合排查哪个模组塞了一堆垃圾。

## 迅步

一个 Baubles 饰品：**戴在身上同时提高飞行速度和移动速度**，右键可以打开界面自己调倍率。
图标参考《全境封锁2》的「迅步」具名手枪。

### 怎么拿 / 怎么用

合成（矿物词典配方，装了别的模组也成立）：

```
羽毛   金锭   羽毛
金锭   钻石   金锭
羽毛   金锭   羽毛
```

| 操作 | 效果 |
| --- | --- |
| **右键（拿在手上）** | 打开速度调整界面 |
| **潜行 + 右键** | 装备到第一个能收它的空饰品槽 |
| 在背包界面里拖进饰品槽 | 同样可以装备（Baubles 的常规做法） |

> 一个右键只能干一件事，而这个物品最需要的是调整界面，所以装备让给了潜行右键。
> 调过速度之后物品会有附魔光效，一眼能看出「这个是开过加速的」。

### 调整界面

飞行和移动**各一组控件**，互不影响：

- 六档预设：**1x / 2x / 3x / 5x / 10x / 16x**（超出配置上限的会置灰）
- 微调：**-0.25 / +0.25**
- 每组都实时显示倍率和换算出来的实际速度

**注意**：调到多少，取决于**服务端配置的上限**（默认 16 倍）。
客户端界面按自己配置画按钮，但发上去的值会在服务端再夹一次 ——
所以服务器主把这个值调小之后，改过的客户端也开不出火箭来。

### 飞行速度为什么会被别的模组吃掉（真踩过的坑）

**症状**：飞行速度在开发环境里好好的，装进完整整合包就完全没效果 —— 移动速度却正常。

**根因是客户端一 tick 内的执行顺序。** 全部来自原版源码：

```
1. gameMode 阶段  Minecraft.runTick → PlayerControllerMP.updateController
                  → NetworkManager.processReceivedPackets()
                  ← S39 包在这里到达，把 flySpeed 覆盖成服务端那份（默认 0.05）
2. level 阶段     theWorld.tick() → thePlayer.onUpdate()
   a. EntityPlayer:259  onPlayerPreTick   → PlayerTickEvent(START)
   b. EntityPlayer:327  super.onUpdate()  → onLivingUpdate() ★ 这里读 flySpeed 算移动 ★
   c. EntityPlayer:392  onPlayerPostTick  → PlayerTickEvent(END)
```

本模组原来**只在 END 阶段设置** —— 也就是在移动算完之后才写。在只有自己改
`flySpeed` 的环境里这没问题（上一 tick 写的值能活到下一 tick 的移动），所以
开发环境（`runClient17`）里一切正常。

但整合包里有 **Draconic Evolution**：它的 `CustomArmorHandler.onPlayerTick`
不管你有没有穿它的护甲，都会在客户端把 `capabilities.setFlySpeed(0.05F)`
写回去，并且会让服务端回一个 S39 包 —— 那个包正好落在上面的第 1 步。
于是每 tick 的移动读到的都是 0.05，**我们的倍率永远轮不到被使用**。

> 顺带一提，`flySpeed` 在整个原版里只有两处：读是
> `EntityPlayer:1855`（`moveEntityWithHeading`），写是
> `NetHandlerPlayClient:1572`（S39 包）。任何"飞行速度不生效"都可以先去
> **F3 调试屏**看那一行 `ws: ..., fs: ..., g: ..., fl: ...` ——
> 它就是这两个值的实时读数。

**修法：START 阶段也设一次**（它在移动之前，设完本 tick 立刻生效），
END 那次留着兜住"别的模组在我们之后又改掉"的情况。

> 排查时可以搜一遍整合包里还有谁在写 `func_75092_a`（`setFlySpeed` 的 SRG 名）。
> 本包里有三个：Draconic Evolution、HardcoreEnderExpansion、以及本模组。

### 飞行速度在服务器上还会被拉回（以及为什么上限是 16）

这是踩过的坑，数字全部来自原版源码：

```
飞行时每 tick 的水平加速 = flySpeed = 倍率 × 0.05
飞行时每 tick 的水平阻力 = 0.91        （EntityLivingBase.moveEntityWithHeading）
终端速度               = flySpeed / (1 - 0.91) = 倍率 × 0.5556 格/tick
服务端判定             = 位移平方和 > 100，即 位移 > 10 格/tick
                        （NetHandlerPlayServer.processPlayer）
⇒ 倍率 ≤ 10 / 0.5556 = 18.0
```

校验一下这个系数：代倍率 1 进去是 0.556 格/tick = **11.1 格/秒**，
正好是创造模式飞行的体感 ✓。

`NetHandlerPlayServer` 里那段是这样的：

```java
double d10 = d7 * d7 + d8 * d8 + d9 * d9;   // 每轴取 max(|位移|, |motion|)
if (d10 > 100.0D && (!this.serverController.isSinglePlayer()
                     || !this.serverController.getServerOwner().equals(this.playerEntity.getCommandSenderName())))
{
    logger.warn("... moved too quickly! ...");
    this.setPlayerLocation(lastPosX, lastPosY, lastPosZ, ...);   // ← 拉回原地
    return;
}
```

**注意那个 `isSinglePlayer` 条件：单人存档里只要你就是房主，整条检查会被跳过。**
所以这个坑的表现是**「自己开档好好的，一连服务器飞行就完全没效果」** ——
不是"慢了一点"，而是**每 tick 都被拉回原地，一点加速都拿不到**。

> 所以**默认上限是 16 而不是 18**：18 是硬上限、零余量，
> 斜着飞或者带垂直分量时位移的平方和会更大，容易擦线。
>
> 另外客户端在多人服务器上会**自动把飞行倍率压到安全值**，
> 并在界面上显示一行红字说明。压到安全值总比维持一个「按了没反应」的倍率强。

> **想在单人里开更快**就把 `swiftStepMaxMultiplier` 调大 —— 单人不受这条限制。
> 但要注意局域网里**别人**连进来时他们仍然会被检查（豁免只对房主生效）。

### 两项速度的实现机制完全不同

这不是设计选择，是 1.7.10 逼出来的 —— 这两项在原版里本来就走两条路：

**移动速度走「移动速度属性」，服务端权威。**

```java
// EntityPlayer.onLivingUpdate()
if (!this.worldObj.isRemote)          // ← 只在服务端
{
    iattributeinstance.setBaseValue((double) this.capabilities.getWalkSpeed());
}
this.setAIMoveSpeed((float) iattributeinstance.getAttributeValue());
```

原版每 tick 在服务端把 `walkSpeed` 写成该属性的基值。所以只要挂一个
`AttributeModifier` 上去就行：公开 API、服务端权威、还会自动同步给客户端。

运算方式用的是 1.7.10 里的 **operation 1（乘基值）**、`amount = 倍率 - 1`。
这个数字不是猜的，`ModifiableAttributeInstance.computeValue()` 里写得很清楚：

```
operation 0:  d0 += amount
operation 1:  d1 += d0 * amount      ← 乘基值
operation 2:  d1 *= (1 + amount)
```

用 0 会变成加法（不按比例），用 2 则会连其它修饰符一起放大。

**跳跃 / 空中的前进速度走的是另一个量，所以必须单独处理。**

`EntityLivingBase.moveEntityWithHeading` 里地面和空中用的根本不是同一个值：

```
地面：f4 = getAIMoveSpeed() * 0.16277136 / (阻力³)   ← 来自移动速度属性
空中：f4 = jumpMovementFactor                        ← EntityLivingBase 上的常量字段
```

`jumpMovementFactor` 和属性没有任何关系，默认固定 0.02 —— 于是会出现
**「走着 5 倍，一跳起来就掉回原版速度」**。

原版这两个值本来是配平的：

```
地面终端 = 0.1 * 1.0 / (1 - 0.546) ≈ 0.2203 格/tick     （0.546 = 方块滑度 0.6 × 0.91）
空中终端 = 0.02 / (1 - 0.91)        ≈ 0.2222 格/tick
```

差 0.9%，基本相等。所以只要把 `jumpMovementFactor` 按**同一个倍率**放大，
空中就又和地面配平了 —— 实现就是 `jumpMovementFactor = 0.02 × 移动倍率`。

> 疾跑时原版会给空中加速度额外加 `speedInAir * 0.3`，而地面那侧是
> `AttributeModifier(..., 0.3, op=2)` = ×1.3。我们整个覆写这个字段，
> 所以自己把 ×1.3 补回去，否则「疾跑跳」会比原版还慢。

时序上不需要每 tick 抢：`EntityPlayer.onLivingUpdate` 先做移动（第 612 行），
**之后**（第 620 行）才把 `jumpMovementFactor` 从 `speedInAir` 重置回来，
而 `PlayerTickEvent(END)` 在那之后 —— 我们写的值会保留到下一 tick 的移动被读到。

摘掉饰品也不用还原：不戴时我们什么都不写，原版第 620 行每 tick 自己就重置回去了。

**飞行速度没有属性可用，只能在客户端改。**

它就是 `PlayerCapabilities.flySpeed` 这个私有字段，而 setter 标着
`@SideOnly(Side.CLIENT)` —— **服务端那份类里根本没有这个方法**，调了会
`NoSuchMethodError`。它本来就是纯客户端参数：在
`EntityPlayer.moveEntityWithHeading` 里被读出来赋给 `jumpMovementFactor`，
那段代码跑在客户端。

而**不能**用反射去写服务端那个私有字段：那样得把字段名 `"flySpeed"` 写死在代码里，
生产环境的 jar 是混淆过的，字段名会变成 SRG 名（`field_XXXXXX`），
运行时直接 `NoSuchFieldException`。

> 顺带一提：移动速度的属性修饰符是**两端都挂**的。服务端那份是权威，
> 客户端那份是为了即时生效（不等属性的网络同步）。两边用同一个 UUID，
> 所以不会叠成双倍。

还有一个细节：迅步摘掉之后，飞行速度会**还原成接管前的值**，而不是无脑恢复成
原版的 `0.05`。万一还有别的模组也在动 `flySpeed`，这样才不会被我们抹掉。

### 配置

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `enableSwiftStep` | `true` | 是否注册迅步 |
| `swiftStepMaxMultiplier` | `20.0` | 速度倍率上限（原版速度的倍数），**以服务端为准** |

> 原版飞行速度是 `0.05`，移动速度是 `0.1`。倍率是对它们分别相乘的。

### 关于依赖

迅步需要 **Baubles**（GTNH 自带）。没装的话物品不会被注册，模组其余部分照常工作。

这里有个坑值得记一笔：**Baubles-Expanded 的 modid 是 `Baubles|Expanded`，真的带一个竖线**，
而竖线正是 FML 依赖串里的「或」分隔符 —— 在 `@Mod(dependencies = ...)` 里写
`required-after:Baubles|Expanded` 会被解析成「Baubles 或 Expanded」，语义完全不对。
所以改成在代码里用 `Loader.isModLoaded` 守卫注册（两个候选 id 都试）。

## 寻物魔杖

一句话：**选一种方块或一条矿脉，它告诉你最近的那个在哪，并且能把你送过去。**

### 怎么拿 / 怎么用

```
 金锭
 末影之眼  指南针  末影之眼
 金锭
```

| 操作 | 效果 |
| --- | --- |
| 右键 | 打开选择界面 |
| 潜行 + 右键 | 取消当前追踪 |

界面里左边是网格（带搜索框），右边是状态面板，上面有两个页签：

| 页签 | 找什么 |
| --- | --- |
| **方块** | 所有方块里的某一种 |
| **矿脉** | GT 的某一条矿脉（见下文「按矿脉搜索」） |

搜索框和共享背包那边是同一套语法（拼音、`@模组`、空格为「与」），
具体见上面[「搜索语法」](#搜索语法)与[「用拼音搜中文名」](#用拼音搜中文名)。

- **左键点一个条目** = 开始搜索最近的那个。搜索是**服务端**做的，界面上的进度条画的就是服务端推回来的进度。
- 找到之后关掉界面（`Esc` 或 `E`），世界里会出现一条从你眼睛连到目标的**光束**，
  目标方块上还有一根光柱和一个线框。光束只在**主手拿着魔杖**时才画。
- 面板上的「传送」按钮会把你送到目标附近。

> **关掉界面不会取消追踪** —— 你正是要关掉界面去看那道光束的。
> 取消有两个入口：界面里的「停止」按钮，或者潜行右键。

### 按矿脉搜索

**为什么需要这个：** GT 的矿脉由**四种材料**铺成（主 / 次 / 中 / 散），
铺成一个横跨好几个区块的椭球；而且同一条矿脉在**不同的石头里是不同的方块**
（GTNH 里石头、花岗岩、深海石头各是一个独立的 `GTBlockOre`）。

于是按方块搜有两个别扭的地方：

1. 你想找的是「铁矿脉」，不是「某个石种下的那块铁矿石」；
2. 按方块找**永远只能找到其中一个石种的那份** —— 如果你站在花岗岩区，
   而搜的是石头版的铁矿石，那是一片都找不到的。

矿脉页签解决这两件事：**选中一条矿脉，按它的主材料去找，跨石种。**

| 你看到的条目 | 意思 |
| --- | --- |
| 铁矿脉 | 主材料是铁的那条脉 |
| 铜矿脉 | 主材料是铜的那条脉（次要材料可能是锡，鼠标悬停能看到四个材料） |

点进去之后：

- 搜索**只在矿脉自己的生成高度区间内做**（悬停条目能看到区间）。
  这既是提速（少扫一大半），也是提精度 —— 区间之外的同类矿石只可能是玩家自己放的。
- 找到的位置就是那条脉上最近的一块矿，光束指着它。
- 只列出**当前维度能生成**的矿脉，下界里不会看到主世界专属的条目。

> **只按主材料定位，不认次要 / 中层 / 散乱那三种材料。**
> 主材料只占一条脉的约 2/7，但它**定义**了这条脉；另外三种材料会同时出现在
> 好几条别的脉里（铁在好多脉里都是次要材料），认它们的话，
> 搜「铁矿脉」会把你带到一条根本不含铁的脉上去。
>
> **找不到的情况**：矿脉是分石种的，有些脉只长在特定的石头里。
> 如果附近全是别的石种，搜出来就是「附近没有找到」——
> 那时候换个搜索方向或者走远一点，而不是以为坏了。

### 传送落在哪

传送**不会**把你塞到目标方块里。服务端会在目标周围按「由近到远」的螺旋顺序
找第一个能站人的位置，判定条件是：

1. 脚下那一格是**实心**的（能站）；
2. 身体占的两格（脚、头）**都不是**实心的（不卡墙）；
3. 头部上方还要留一格空（不顶天花板）。

一个都找不到（比如目标整个埋在山体里、或者悬在半空）就**不传送**，
只在聊天栏告诉你一声。宁可让你自己挖过去，也不能把你塞进石头里 ——
1.7.10 的 `EntityPlayerMP` 没有「卡墙自动推出来」那套逻辑，
真塞进去了就是一直窒息，而且服务端还会因为你「移动异常」把你拉回去。

传送成功后这次结果会被清掉：同一次扫描只允许传送一次，
否则「找到 → 传送 → 再传送」会变成廉价的地图跳跃。

### 搜索是怎么做的

几个关键取舍：

- **搜索必须在服务端。** 客户端只有自己视野附近的区块，想找 64 格外的方块根本看不见；
  而且「最近的在哪」这件事必须由权威方回答，否则改个客户端就能让魔杖指向一个不存在的坐标，
  然后把你传送到虚空里。
- **增量扫描，不是一口气扫完。** 半径 128 的正方体是 1350 万个方块位置，
  一口气扫完服务器要卡好几秒。所以拆成每 tick 固定预算的任务，扫不完留到下一 tick。
- **按水平环由近到远推进**（切比雪夫距离一圈圈往外）。
  边扫边记最近的那个，一旦当前环号已经比已知最近距离还远，外面不可能有更近的，
  直接结束 —— 大多数查询根本扫不满整个半径。
- **只扫已加载的区块。** 不挡这一下的话，扫一个半径 128 的范围会把上千个区块
  从磁盘上加载出来，那是比卡顿严重得多的事故。
- **直接从区块的方块数组读**，不走 `World.getBlock` —— 后者要处理光照、邻接、
  TileEntity 等一堆东西，在纯读取的场景下全是开销。

同一个玩家同时只允许有一个进行中的扫描：重新选一个方块就把旧的顶掉。
不限制的话，一个连点器就能让服务器同时跑几十个扫描任务。

### GT 的矿石：为什么不能只比元数据
GT 把矿石的**全部信息编码在元数据里**，而不是靠不同的方块 id：

```
meta = 小矿标志 * 16000  +  自然标志 * 8000  +  石种 * 1000  +  材料索引
```

一个 `GTBlockOre` 方块要表示成百上千种矿，所以元数据的值远超 15 ——
这靠 GTNH 里的 **EndlessIDs**（它扩展了方块元数据的位宽）撑着。

其中**「自然标志」这一位专门用来区分「世界生成的」和「玩家放下的」**：
`OreManager.getOreBlockForWorldGen` 里写死了 `isNatural = true`，
而创造标签页里那份（也就是你能在寻物界面选到的那份）是 `false`。

> 如果只做「元数据精确相等」，就会出现一个很诡异的现象：
> **自己放下的矿永远找得到，世界生成的矿怎么都找不到** ——
> 因为放置走的恰好就是 `isNatural = false` 那一份，跟搜索目标天然一致。
>
> 所以对 GT 矿石改成了比较**矿的身份**（材料 + 石种 + 大小矿），
> 把自然标志位排除在外：搜「铁矿石」，自然生成的和自己放下的都能找到，
> 但不会串到铜矿石上去。

比较用的是 `GTBlockOre` 自己的公开解码方法（`getMaterialIndex` / `getStoneIndex` /
`isSmallOre`），而不是在外面重算位移取模 —— 编码是 GT 的内部约定，
让它自己解码才不会在 GT 改动时错位。这段代码单独放在 `locator/GtOreSupport.java` 里，
并由调用方用 `try/catch` 包住：万一换到一个没有 `GTBlockOre` 的 GT 版本，
会退化成精确匹配（并打一条警告），而不是让整个扫描崩掉。

> ⚠️ **注意传送。** 这个修复只解决「找到」。GTNH 的矿大多埋在整块石头里，
> 而传送要求目标附近有能站人的空位（见上文「传送落在哪」），
> 所以搜到了深层矿脉之后点传送，很可能得到「找不到能站人的地方」。
> 这不是 bug，是「不把你塞进石头里」的代价 —— 那种情况请自己挖过去。

### 「所有方块」这个列表是怎么来的

GTNH 里方块条目有几万条（GT 的某个元数据方块自己就能贡献几千个变体），
一次性枚举会卡住好几秒。所以客户端是**分帧建立索引**的：每 tick 只处理固定预算，
界面上显示「正在建立方块索引… 37%」。建完一次之后整个客户端会话都复用。

搜索文本（显示名 + 注册名 + 拼音，预先转小写）在建索引时就一起算好了：
搜索是每敲一个键就要扫全表的，现算的话几万次 `getDisplayName()` 会明显卡顿。

搜索语法：

| 写法 | 含义 |
| --- | --- |
| `iron` | 包含 `iron` 的方块 |
| `iron block` | 同时包含 `iron` 和 `block` |
| `@gregtech` | 注册名里带 `gregtech` 的（等价于按模组过滤） |
| `tiekuang` | 拼音全拼：找到名字里有「铁矿」的方块 |
| `tks` | 拼音首字母（见上文「用拼音搜中文名」） |

### 配置

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `enableLocatorWand` | `true` | 是否注册寻物魔杖 |
| `locatorSearchRadius` | `128` | 搜索半径（方块）。扫描量按**三次方**增长 |
| `locatorBlocksPerTick` | `200000` | 每 tick 检查多少个方块位置 |
| `locatorScanTimeoutTicks` | `600` | 一次扫描最多跑多少 tick，超时放弃（兜底） |

全部只在服务端生效，客户端配置里的数字不影响判定。

> 半径 128 扫满一遍约 1700 万次方块读取。默认预算下最坏情况（附近完全没有这种方块）
> 大约 1~2 秒出结果；正常情况因为环形提前退出，通常几 tick 就结束了。
> 把 `locatorSearchRadius` 加到 256，扫描量就是 **8 倍**，请配合调大 `locatorBlocksPerTick`。

### 已知限制

- **结果不能跨维度。** 搜索只在玩家当前维度做。出结果之后如果你走了传送门，
  界面会提示「结果在另一个维度」，传送按钮也会禁用，光束同样不画 ——
  免得把你引到一个坐标数字相同、但完全是另一个世界的地方。
- **不搜未加载的区块。** 这是刻意的（见上）。所以「世界上最近的」实际上是
  「已加载区域里最近的」。
- **传送是直接设置坐标**，不走传送门。目标区块没加载的话会被顺带加载出来。
- **搜索框里打不出中文**（1.7.10 的输入层没有输入法支持，见上文
  「用拼音搜中文名」），所以搜索请用拼音 —— 全拼和首字母都认。
- **矿脉是按主材料定位的**，不是按「这条脉的几何范围」。所以报出来的是
  「这条脉上离你最近的一块矿」，而不是脉的几何中心 —— 对「过去挖」这件事来说，
  前者更有用。矿脉本身不落盘，GT 只在生成区块时算一次，没法反查它的边界。
- **矿脉页签依赖 GT 的 API。** 拿不到（换了 GT 版本）时这个页签会直接不显示，
  方块搜索照常可用，不会崩。

## 自动化对接

「共享终端」方块不只是个界面入口，它同时把自己伪装成一个**无限容量的容器**，
让 GT 的管道、泵、流体覆盖板能直接读写共享存储：

### 流体

- **往外抽**：抽的是这个终端**当前选中的流体**。
  在界面里对着流体条目按中键即可设置，界面的状态行会显示当前选的是哪种。
- **往里灌**：管道送进来的流体直接进共享存储，不需要任何设置。

### 物品

物品管道、漏斗往里塞的东西会被**立刻吸收**进共享存储。

只进不出是刻意的：从方块抽物品需要「抽哪一种」的语义，
硬塞给管道反而容易误操作 —— 取东西交给界面里的搜索更合适。

> 方块本身**不缓存任何东西**，所有读写都是直通共享存储的。
> 所以放多少个终端都不会出现「东西在哪个终端里」的问题。

## 数据在哪 / 备份

```
<存档目录>/data/futa_gtnh_shared.dat      正式文件
<存档目录>/data/futa_gtnh_shared.dat.bak  上一份备份
```

跟着存档目录（主世界，维度 0）走，所以**所有维度共用同一份数据**。

写入是这么保证安全的：

1. 先写 `.tmp`；
2. 把上一份正式文件**复制**成 `.bak`；
3. 用 `ATOMIC_MOVE` 把 `.tmp` 换成正式文件。

所以中途断电 / 崩服不会留下半个文件。第 2 步用复制而不是移动，是为了不留「正式文件已经挪走、
新文件还没就位」的窗口期 —— 那个窗口里一旦替换失败，正式文件就没了。

主文件读不出来时会自动回退到 `.bak`；**主文件整个不见了**（正是上面那个窗口期的样子）
也会去看一眼 `.bak`，而不是当作「从来没有过数据」直接空手启动。
两个都读不出来时以空存储启动并保留原文件（崩服比丢数据更糟，而且留着文件还有人工抢救的余地）。

### 关于「临时卸载模组」

存档里读不出来的条目（对应的模组被卸了、流体没注册名字了……）**不会被丢掉**，
而是原样存在内存的「隔离区」里，写盘时再原封不动写回去。

这一点很关键。如果读不出来就丢，那么「临时卸载一个模组 → 启动一次服务器」就足以
**永久抹掉**那个模组的所有物品：内存里没了 → 第一次自动保存覆盖正式文件 →
第二次保存把备份也轮换成新的空文件 → 连 `.bak` 都救不回来。
留着原始 NBT 的话，把模组装回去，东西就还在。

启动日志会告诉你暂存了多少条：

```
共享存储：已从 futa_gtnh_shared.dat 载入 1234 种物品 / 56 种流体（另有 87 / 3 条因缺少对应模组被暂存）
```

## 已知限制

把当前版本**做不到**的事情集中列一下，免得你花时间找：

| 限制 | 说明 |
| --- | --- |
| **合成栏只有 3×3** | 从共享存储取料/自动合成都走终端界面右侧的 3×3 合成栏。行列超过三档的配方（某些 GT 多方块结构）不参与 —— 归一化时排不出对应的格位，宁可不出填充按钮也不摆错形状。 |

| **没有自动合成计划** | NEI 联动的自动合成是「按这一条配方连续做」，不是 AE2 那种「缺什么自动规划原材料」的合成树。 |
| **没有权限控制** | 所有人自由存取，这是设计选择。需要限制的话得靠领地插件把共享终端方块围起来。 |
| **界面比较宽（232px）** | 因为右侧有装备栏和合成栏。打开界面时 NEI 的物品面板会自动收起（`hideNeiPanelInTerminalGui` 可关），底部搜索条保留。 |

`locator/` 里有两个类是专门用来<b>隔离 GT 版本差异</b>的，它们直接引用 GT 的类型，
调用方一律用 `try/catch` 包住：

| 类 | 干什么 | 拿不到 GT API 时 |
| --- | --- | --- |
| `GtOreSupport` | 解矿石元数据、按材料识别矿石、取矿脉图标 | 退回精确元数据匹配 |
| `OreVeinCatalog` | 包装 GT 的矿脉列表 | 「矿脉」页签不显示 |

### 几个关键设计决定

**1. 数量用 `long`，不放进 `ItemStack`**

`ItemStack.stackSize` 是 `int`，而原版 `ItemStack.writeToNBT` 把 `Count` 写成
**byte**（超过 127 会被截断）。所以「无限堆叠」必须在**存储层**摆脱
`ItemStack` 的数量语义：条目存 `long`，只在取到玩家背包时才落回 64 一组。

**2. 存储键是「物品 + 元数据 + NBT 的深拷贝」**

`ItemKey` / `FluidKey` 会深拷贝 NBT 并把空标签归一化成 `null`。
不拷贝的话，调用方一改 NBT（GT 机器改电池电量就是这么干的），
键的 `hashCode` 就变了，存进 `HashMap` 之后再也查不出来。

1.7.10 里所有 NBT 标签类型（含 `NBTTagList`、`NBTTagByteArray`、`NBTTagIntArray`）
都按内容实现了 `equals`/`hashCode`，所以直接复用原版 NBT 的比较语义是安全的 ——
附魔书、GT 工具、电池这类靠列表型 NBT 区分的物品不会互相串条目。

**3. 服务端权威，只有一条改动路径**

原版的 `Container.slotClick` **两端都会跑**
（客户端 `PlayerControllerMP.windowClick` 会先本地跑一遍再发包）。
所以 `ContainerSharedTerminal` 在服务端不做任何实际增删，
客户端也只负责「发请求包」；真正的改动全部集中在 `StorageActionHandler` 一处，
由它统一校验服务端状态。

代价是客户端不做本地预测：Shift 点击后物品要等一个 tick（约 50ms）才消失。
换来的是**永远不会出现客户端有、服务端没有的幽灵物品**。

> 唯一的例外是合成栏和产物格，见下面第 5 条 —— 它们是真实状态，走原版。

**4. 虚拟槽位**

共享存储可能有上万个条目，不可能给每个都建一个真的 `Slot`。
所以界面上只放**当前这一页**的显示用物品（`GhostInventory`），
但对整个原版 GUI 体系来说它就是普通槽位 —— 所以：

- 对着共享存储里的物品按 **R/U 查 NEI 配方直接可用**；
- 原版的 tooltip、高亮、Shift 点击分发都照常走。

`GhostInventory` 的写入对 `null` 免疫：容器重新同步时原版会对每个槽位调用
`putStack(null)`，如果把它当成一次「存入」，那就是刷物品漏洞。

`SlotSharedStorage.isItemValid()` **刻意返回 `false`**，这反直觉但很重要：
`putStack` 是有意的空实现（往虚拟槽位直接塞东西这条路上，「物品从哪来」说不清，
任何实现都可能变成刷物品漏洞），一个嘴上说「我能收」、实际什么都不做的槽位是在撒谎。
NEI 的配方转移会遍历容器找目标槽位，它要是挑中了虚拟格，
整个转移就会悄无声息地什么也不做 —— 而界面右侧明明有真正的合成栏。
玩家点击这些格子走的是 `slotClick` 里那条独立的拦截分支，**根本不查 `isItemValid`**，
所以取用完全不受影响。

**4b. 条目的「键」不能从显示物品反推**

这一点是踩出来的。原来点击某一格时是这么拿键的：

```java
ItemStack display = ghost.getDisplay(i);
ItemKey key = ItemKey.of(display);      // ← 从显示物品反推
```

当时的理由是「显示物品就是 `key.prototype()` 造出来的，反推无损」。
**这个前提在别的模组会改写物品栈时不成立。**

GT 的 `MetaGeneratedTool.getToolStats()` 就是一个<b>有副作用的 getter</b>：
它内部调 `isItemStackUsable(stack)`，而那里面会
`ItemStackNBT.removeTag(stack, "ench")`，还会用
`EnchantmentHelper.setEnchantments(附魔表, stack)` 把附魔表<b>重写</b>回去。
而 `getToolStats` 在物品渲染和 tooltip 里都会被调到 —— 于是
**光是把界面画出来，显示栈的 NBT 就已经和存档里的不一样了**。

结果就是：键反推出来对不上，服务端查不到条目，**点击完全没反应**，
而且客户端和服务端都一个字都不说。实测症状（服务端日志）：

```
共享存储：玩家 fyt 请求取出一个存里没有的条目 ItemKey[gregtech:gt.metatool.01@18+nbt]（数量 1），已忽略
```

存档里明明有 `meta=18` 那一条 —— 差别只在 `ench` 上。

所以现在**键跟着显示物品一起送进容器**（`setPageDisplay(page, itemKeys, fluidKeys)`），
点击时直接用带过来的键；从显示物品反推只保留为兜底。

> 教训：只要一个 `ItemStack` 会被别的模组拿到（而渲染、tooltip 都会），
> 就不能把它的 NBT 当作稳定身份。**身份要在源头记下来，而不是事后反推。**

**5. 合成栏和产物格走原版，不进那条「单一改动路径」**

这是上面第 3 条的唯一例外，而且是刻意的：合成栏（`InventoryCrafting`）和产物格
是**真实状态**，两端都有、由容器自己同步，所以交给原版处理最稳。
尤其是产物格的 Shift 连续合成，靠的是原版 `slotClick` 里
「`transferStackInSlot` 返回非 null 就 `retrySlotClick` 再来一遍」这个循环 ——
硬塞进我们那条只会返回 `null` 的路径，会把这个循环直接掐死。

**6. 合成栏属于容器，不属于玩家**

1.7.10 里合成栏是 `ContainerPlayer` 私有的 `InventoryCrafting`
（`ContainerPlayer.java:18`，原版是 2×2；本终端自己建了一个 3×3 的），
`InventoryPlayer` 上**没有** `craftingInventory` 这个字段。
所以打开终端时原版会先 `closeContainer()`，`ContainerPlayer.onContainerClosed`
把它那 4 格丢到地上。这不是本模组引入的 —— 开任何箱子、任何容器都一样。

也正因为如此，`DEPOSIT_CRAFT_SLOT` 是独立的网络动作：
合成栏没法用「玩家背包索引 0..39」那套编号表达，服务端得去操作自己容器里的那个
`craftMatrix`。

**7. 全量同步 = 整体 gzip + 按字节切片**

不做「按条目分包」：那样要么每包都带 NBT 头开销，要么得猜每包塞多少条才不超长。
整体压缩后切片，压缩率最好，而且每片大小是确定的，不可能超长。
服务端把压缩结果缓存起来复用（共享存储是全服共用的，所有玩家拿到的是同一份字节）。

**8. 增量同步带绝对值而不是增减量**

绝对值是幂等的：丢一条、重复一条都只会短暂显示错误，下一条就会纠正过来。
增减量在丢包或乱序时会让客户端和服务端算出不同的结果。

**9. 数量守恒**

`InventoryExchange` 里所有操作都遵循「先把能放多少算清楚，再从另一边扣，
任何一步失败都把已经扣掉的还回去」。宁可这次操作什么都不做，
也绝不能出现「背包里没拿到、存储里却少了」。

`takeFluidDisplay` 还会在给出显示物品之后**读回来核对 GT 到底记下了多少**，
GT 那边如果截断或拒收就把差额还回存储。

### 兼容性相关的坑（都已处理）

| 坑 | 处理方式 |
| --- | --- |
| `ItemStack.writeToNBT` 把 id / Damage 写成 `short` | 持久化和网络都自己写 `int` 型 id |
| `FluidRegistry.getFluidName(Fluid)` 对未注册名字的流体返回 **null**，而 `NBTTagString(null)` 会抛异常 —— 放任的话**整份存档的保存会永久失败** | 建键时就把没有名字的流体挡在门外，`writeToNbt` 再兜一次 |
| `GTUtility.getFluidDisplayStack(fs, boolean)` 的布尔量是 `aShowAmount`，传 `false` 会把数量写成 0 | 传 `true`，并读回来自校验 |
| GT 的流体显示物品没覆写堆叠上限，会被原版合并成一叠，而它的数量整体存在 NBT 里、不可拆分 | 按 `数量 × 堆叠数` 整叠结算，要么全收要么不动 |
| 流体容器也会成叠（16 个牛奶桶），而 `FluidContainerHelper.drain` 返回的只是**一个**容器的量 | 倒料/灌装一律按 `单个量 × 堆叠数` 结算，并且整格替换而不是一个个换 |
| 光标上的物品不属于 `mainInventory`（它是 `InventoryPlayer.itemStack`），背包遍历碰不到 | 倒空光标容器单独走一条动作 `DRAIN_CURSOR` |
| FML 的 `TickEvent` / `InputEvent` / `PlayerEvent` 在 `FMLCommonHandler.instance().bus()` 上，不在 `MinecraftForge.EVENT_BUS` | 注册到正确的 bus（注册错了会**静默失效**） |
| 1.7.10 的 `SimpleNetworkWrapper` 直接调用 `onMessage`，不切主线程 | 依赖原版 `NetworkManager` 把包排队到主线程处理 |
| `Container.transferStackInSlot` 基类实现会无限递归 | 覆写并统一返回 `null`（产物格除外） |
| 原版「双击收集」会遍历所有槽位并直接改大光标堆叠数 | 在光标非空时直接不处理，等服务端纠正 |
| 原版 `ContainerPlayer` 在背包装不下整份产物时仍会扣掉全部材料，多余产物蒸发 | 先确认整份产物放得下才合成 |
| `ItemStack.getMaxStackSize()` 返回异常值 | 退回 64，避免 0/负数导致死循环 |
| 容器槽位下标 ≠ `mainInventory` 下标（槽位 45 对应 `mainInventory[9]`） | 一律用 `Slot.getSlotIndex()` 换算，并校验 `slot.inventory` |
| 模组被卸载导致物品 / 流体读不出来 | 原样留在内存的「隔离区」，写盘时写回去，装回模组东西还在 |
| 原版 `GuiButton` 高度 ≠ 20px 时按钮贴图底边被裁掉，按钮看起来和背景边框「长在一起」 | 自绘按钮（`client/GuiSmallButton.java`）：上下两半分别对齐贴图区段顶部/底部采样，任意高度都有完整边框 |
| lwjgl3ify（LWJGL3/新 Java）下 IME 字符事件 keyState 恒为真，旧的「>255 字符注入」会失效或重复 | `client/ImeCompat.java` 探测 lwjgl3ify 的 `TextFieldHandler` 在不在：在 → 走它对 GuiTextField 的自动注入；不在 → 保留旧路径（InputFix 场景） |
| NEI 的配方转移只认玩家背包且靠模拟点击，无法从共享存储取料 | 自己的 overlay handler 把布局打包发给服务端直填合成栏（`exchange/CraftFiller.java`），不模拟点击 |
| MouseTweaks 的「滚轮 tweak」会**替玩家合成点击**打在鼠标下的格子上，共享格「点一下 = 取一个」，于是滚轮滚一格就掉一个物品 | 终端界面实现 MouseTweaks 的 `IMTModGuiContainer` 接口并让 `isWheelTweakDisabled()` 返回 true（`client/MouseTweaksCompat.java`） |
| **NEI 也有一个「滚轮转移物品」**（`inventory.disableMouseScrollTransfer`），而且装了 NEI 时 MouseTweaks 会让位给它 —— 所以真正在掏东西的是 NEI（`NEIController.mouseScrolled` → `FastTransferManager`） | 把终端界面登记进 NEI 的 `GuiInfo.customSlotGuis`（`NeiIntegration.register()`）：`hasCustomSlots` 是 `mouseScrolled` 的第一道判断，且全 NEI 只有这一处用到它 |

### 为什么滚轮以前会掏出物品（NEI 与 MouseTweaks 的「滚轮搬运」）

**结论先说**：滚轮掏东西不是本模组的逻辑，而是**别的模组在替玩家点格子**。整合包里同时有
两个「滚轮滚过格子就把物品在两边搬一次」的功能，而且它们之间还有先后关系：

| 谁 | 开关 | 在本界面上做什么 |
| --- | --- | --- |
| **NEI** | `config/NEI/client.cfg` 的 `disableMouseScrollTransfer`（默认 false = 开着） | 滚轮滚过有东西的格子时，用 `FastTransferManager` 把物品在「容器 ↔ 玩家背包」之间搬一次 |
| **MouseTweaks** | `config/MouseTweaks.cfg` 的 `B:WheelTweak`（默认 true） | 同样的事，但它**在有 NEI 时会让位**：`Runtime.isMouseWheelTransferActive()` = `WheelTweak && !NEI.isMouseScrollTransferEnabled()` |

也就是说：**装着 NEI 时，MouseTweaks 的滚轮 tweak 是关着的，干活的是 NEI**。
（这也是为什么先按 MouseTweaks 修了一版却没效果 —— 那一版并非白做，见文末。）

NEI 那条路是这样的（`NEIController.mouseScrolled`）：

```
GuiContainerManager.handleMouseWheel            ← 读 Mouse.getEventDWheel()
  └ mouseScrolled(dir) → 逐个 IContainerInputHandler.mouseScrolled(...)
      └ NEIController.mouseScrolled
          if (!NEIClientConfig.isEnabled()) return false;
          if (GuiInfo.hasCustomSlots(gui)) return false;        ★ 我们的钩子
          if (!NEIClientConfig.isMouseScrollTransferEnabled()) return false;
          Slot slot = gui.getSlotAtPosition(鼠标);
          if (slot != null && slot.getHasStack()) {
              fastTransferManager.transferItem(gui, slot.slotNumber);   // 或 retrieveItem
              return true;
          }
```

`transferItem` / `retrieveItem` 会去点槽位，最终走到
`ContainerSharedTerminal.slotClick`。而共享格在那里的语义是「左键点一下 = 取 1 个」，
于是**滚一格就掉出来一个物品**（数量恰好是 1，因为那是按「个」合成的一次左键点击）。

**处理办法**：NEI 的 `GuiInfo.hasCustomSlots(GuiContainer)` 就是给这种「槽位语义自己说了算」
的界面准备的逃生门 —— 它只做一件事：`customSlotGuis.contains(gui.getClass())`。
把这个类登记进去，上面那段的第一道判断就会 `return false`，NEI 不再插手滚轮。
（在**整个 NEI 里 `hasCustomSlots` 只被 `mouseScrolled` 用到**，所以登记它不会影响
配方转移、面板、书签等任何别的功能。）

登记在 `client/nei/NeiIntegration.register()` 里：

```java
GuiInfo.customSlotGuis.add(GuiSharedTerminal.class);
Class<? extends GuiContainer> mouseTweaksGui = MouseTweaksCompat.guiClass();
if (mouseTweaksGui != null) GuiInfo.customSlotGuis.add(mouseTweaksGui);
```

第二个是因为：**它用的是 `gui.getClass()` 精确匹配**（`HashSet<Class>`），子类不会自动继承，
而装了 MouseTweaks 时用的正好是兼容子类。

> **急用/暂时不改 jar 的办法（客户端）**：把 `<整合包实例>\config\NEI\client.cfg` 里的
> `disableMouseScrollTransfer` 改成 `true`（游戏里 NEI 设置界面里也有这一项）。
> 这是全局开关，对所有界面生效；说明这个滚轮搬运本身就不是我们独有的问题。
> 注意这是**纯客户端**的事：点击是客户端合成的，所以只更新客户端 jar 就能解决。

### 没有 NEI 的环境：MouseTweaks 的滚轮 tweak

上面那条 `isMouseWheelTransferActive()` 的前提是「装了 NEI」。**没装 NEI 时 MouseTweaks 的
滚轮 tweak 就是唯一在干活的那个**，所以那一侧也要关掉。MouseTweaks 提供了官方兼容接口
`yalter.mousetweaks.api.IMTModGuiContainer`，界面实现它就等于说「这个容器我自己管」：

- `isWheelTweakDisabled()` 返回 true → 它不在这个界面上做滚轮搬运（**唯一的行为改动**）；
- 其它方法照原版语义实现（槽位表就是 `inventorySlots`，`clickModSlot` 依旧转交给
  `handleMouseClick(slot, slotNumber, 鼠标键, shift ? 1 : 0)`），
  所以 MouseTweaks 的拖拽 / 左键 tweak 在本界面里的手感和以前完全一样。

两个实现上的注意点：

1. **接口类型必须隔离在一个懒加载的类里**（`client/MouseTweaksCompat.java` 的嵌套类 `Gui`）。
   没装 MouseTweaks 时那个接口不存在，加载会 `NoClassDefFoundError`；
   外面用 modid + 类名双探测守卫，缺席时照旧 `new GuiSharedTerminal(...)`
   （和 `client/NecharBridge.java` 一个套路）。打开界面统一走
   `GuiSharedTerminal.create(...)`，别直接 `new`。
2. MouseTweaks 会按「界面有没有实现这个接口」把容器分成「模组界面 / 原版界面」两条路
   （`ModCompatibility.getModGuiContainerID`：实现了就是 2，普通原版 `GuiContainer` 是 1）。
   **它在 ID 为 1 时根本不问滚轮开关**（`ContainerContext.isWheelDisabledForThisContainer`
   里 `if (guiContainerID == 1) return false;`），所以「只加一个开关」是不够的 ——
   必须真的把接口实现上，让它把本界面认成 2 号。
   （dev 环境里日志会打 `You have just opened a FutaGTNH 共享存储终端 container …`，
   出现这行就说明接口被认下了。）

### 构建

```bash
gradlew.bat build          # 产物在 build/libs/
gradlew.bat runClient17    # 开发版客户端（★ 不能用 runClient，原因见 README-开发环境.md）
gradlew.bat spotlessApply  # 修正格式
```

需要 **GT5-Unofficial** 和 **lwjgl3ify**（均为硬依赖：存储键和流体显示物品直接用
GT 的 API；中文输入法支持建立在 lwjgl3ify 的 GuiTextField 补丁之上）。
NEI 是可选联动（`after:NotEnoughItems`，配方转移取料 + 界面适配），
NotEnoughCharacters 也是可选联动（装了就复用它的拼音/模糊音匹配），不装都能跑。
MouseTweaks 同样是可选联动：装了就把终端界面上的滚轮搬运关掉（见上文），
不装则那段兼容代码根本不会被加载（dev 环境里也装了一份，方便直接验证）。
