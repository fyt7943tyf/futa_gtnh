# 深空采矿指挥中心

UV 级 7×7×N（2..9 层）多方块：塞入 X 级 Galacticraft 火箭后，在 GUI 里按星球配置**虚拟的** 1-4 级采矿场与流体钻机。虚拟机不加载任何区块——矿机用确定性算法离线复现真实星球的 GT 矿脉，钻机复现当地油田的上界产量。产出与功耗按 GT 原版机器的口径模拟，**不可超频**。

需要 Galacticraft（软依赖：没装时整个功能组——方块、控制器、事件、配方——都不注册）。服务端权威模拟，客户端只负责 GUI 与渲染。

## 使用流程

1. **搭建结构**（7×7 底座 + 可叠加中间层 + 顶盖，2 到 9 层，NEI 结构预览 / 全息投影仪可用）：
   - 底座：采掘桁架地板，**控制器在底座前缘正中**（结构朝控制器背面延伸，整体随控制器朝向旋转），边缘可贴输入总线/输入仓/输出总线/输出仓/维护仓/能源仓；
   - 中间层：桁架边框 + 中央全息投影核心柱；
   - 顶盖：桁架边框 + 内圈的全息核心环 + 正中与外围一圈的信号天线阵列。

   最矮的 2 层结构（底座 + 顶盖）需要 49 个采掘桁架，每多一层 +24。
2. **控制槽放入 Galacticraft 火箭**（任意 `ItemTier{N}Rocket`，等级决定可到达的星球）。火箭是「通行证」，不会被消耗、不吃维护损耗。
3. 打开 GUI，在**星球页**选一颗星球（每页 5 行，底部翻页；列表按火箭等级排序）。状态色：红 = 火箭等级不够，暗灰 = 未勘查（该维度至少要被加载过一次，种子才会被记录），绿 = 有机器在转，金 = 配了机器但都停着，灰 = 还没配置。主世界不在列表里。
4. **配置页**用 +/- 配置各等级采矿场/流体钻机台数（受机位容量钳制），悬停每一行可看这一档的 EU/t、周期、区域；右侧是该星球矿脉的权重分布（百分比，标题行悬停看带数值的完整列表）；钻机可选目标油田流体。
5. **运行页**按「星球 / 类型 / 等级」聚合显示各虚拟机状态（开采中 / 下潜中 / 缺采矿管道 / 缺钻井液 / 无油田 / 区域已采完）；「立即输出」手动倒缓冲；「矿脉重置」作用于星球页里最后选中的那颗（按钮上写明是哪颗）。
6. 输入走输入总线/输入仓，输出走输出总线/输出仓。缺料（管道、钻井液、润滑油）的机器自动暂停、补上后从停下的地方继续；**正在暂停的机器不收润滑油，但仍计入 EU/t**。塞不进输出总线/输出仓的产物按 GT 多方块惯例丢弃。
7. 运行时的外观：控制器正面屏幕点亮，顶盖每根天线射出一道细光，全息核心外面有星环流转，顶盖上方投影出一颗缓缓旋转的星球——显示的是这台机器当前在开采的那一颗（多颗时每 30 秒轮换）。全息核心与天线自身发光，夜里整座塔是亮的。

## 数值口径（对齐 GT 5.09.54.175，勿手工重推）

### 虚拟采矿场（t = 1..4）

| 项 | 公式 | 数值 |
|---|---|---|
| 功耗 | `3·4^(t+1)` EU/t | 48 / 192 / 768 / 3072 |
| 周期 | `baseTime>>(t+1)` tick | 240 / 100 / 40 / 15 |
| 开采区域 | (2R)² 区块，R = 3/4/6/9 | 36 / 64 / 144 / 324 |
| 每周期产出 | 1 矿方块 → 打粉机配方 → 粉碎矿 ×(1~4 随机)；概率副产物没 Roll 中就不产出 | — |
| 钻井液 | 2000mB / 矿（`ItemList.sDrillingFluid`） | — |
| 下潜 | 管道 1 根/周期，深度 = clamp(veinMinY−8, 16, 128)；空区块 16 根 | — |

区块按行优先顺序推进。区域采完后 era+1 原地重置（`autoResetVein=false` 时改为硬停，等手动重置）。

**队列不持久化。**矿石由「星球 seed + era + 区块坐标」确定性决定，存档只记「当前区块还剩几个没挖」，读档后把整块重新模拟出来、跳过已挖的那一截——所以读档不会多给矿，也不会把挖过的矿再发一遍。

### 虚拟流体钻机（t = 1..4）

| 项 | 公式 | 数值 |
|---|---|---|
| 功耗 | `7·4^(t+1)` EU/t | 112 / 448 / 1792 / 7168 |
| 下潜 | 64 根管道，周期 `120>>(t+1)` tick | 30 / 15 / 7 / 3 |
| 到底后周期 | 恒 8t | — |
| 抽取区域 | R×R 区块，R = 1/2/4/8 | 1 / 4 / 16 / 64 |
| 产量 | 区域内**流体 = 所选油田**的区块的上界产量之和 ×`oilYieldFactor`（固定不衰减） | 默认 ×0.8 |

油田上界产量 = `floor(amount × 0.5 / 5000)`（amount 为 GT 五次幂分布 ±25% 抖动后的存量）。没选油田时取该星球权重最大的流体——只累计这一种流体的存量，不会把别的流体算进来再当成它吐出来。

### 共同口径

- **总功率 = 全部可运行虚拟机 EU/t 之和**，不可超频；批次 20t（=1 秒）推进一次。
- **润滑油**：每台每秒 1000mB（`Materials.Lubricant`），批次结算。
- **机位容量** = `8 + (层数−2)×8`（9 层 64 台），GUI 配置时钳制。
- 产物：矿石 → 打粉机配方 → 粉碎矿；材料不限于 GT 自家（BartWorks / GT++ 材料走 `IOreMaterial` 自己的取物口径）。

### 矿脉/油田种子链（确定性复现的核心）

- 矿脉：`oreveinSeed=(seed<<16)^((dim&0xff)<<56|(sx&0xfffffff)<<28|(sz&0xfffffff))` → `nextInt(100)<veinChance` → `FNV1a64` 两次 → `WorldgenQuery.veins().inDimension(dimName).findRandom` → `FNV1a64(attemptSeed, primary.getId())` → 5 次 `nextInt`（minY/westX/eastX/northZ/southZ）→ 9 层逐列放置。
- 种子区块：`floorMod(x,3)==1 && floorMod(z,3)==1`；影响半径 2（`GTWorldgenerator.MAX_VEIN_SIZE`）。
- 油田：8×8 区块共享油藏 `XSTR(seed+dim*2+(cx>>3)+8267*(cz>>3))`。
- 星球维度键 = GC 天体 name（`DimensionDef.DimNames`）；矿脉按 `layer.canGenerateIn(name)` 过滤，油田按数字 dimId 查 `GTMod.proxy.mUndergroundOil`。

## 调试

`/futaspacer planets` 列出星球表；`/futaspacer probe <dimName> <chunkX> <chunkZ> [era]` 输出该星球该区块的模拟矿脉与油田。**与真实星球（探矿仪 / Visual Prospecting / 实地开挖）对照，同 seed 应当一致**——这是验证确定性复现正确性的手段，也是 era 重置后检查分布是否符合权重的手段。

## 配置项（`futa_gtnh.cfg`）

| 键 | 默认 | 含义 |
|---|---|---|
| `enableSpaceMiningCenter` | true | 功能总开关（关闭时方块/MTE/事件都不注册） |
| `spaceMiningCenterMetaTileId` | 32703 | 控制器 MTE id（冲突时启动抛异常，提示改配置） |
| `spaceCenterMinHeight` / `spaceCenterMaxHeight` | 2 / 9 | 结构层数范围（上限硬顶 9） |
| `spaceCenterBaseCapacity` | 8 | 基础机位（2 层时的容量） |
| `spaceCenterCapacityPerLayer` | 8 | 每加一层的机位增量 |
| `spaceCenterLubricantPerMachine` | 1000 | 每台每秒润滑油（mB） |
| `spaceCenterOilYieldFactor` | 0.8 | 钻机产量系数（固定，不随时间衰减） |
| `spaceCenterAutoResetVein` | true | 区域采完是否自动 era+1 原地重置 |

## 已知偏差（离线模拟 vs 实地开采）

1. **矿脉种类取「首个尝试」**：真实世界里矿脉种类由首个处理该种子的区块锁定；虚拟矿机从区域起点向外扩张，与常规世界生成顺序一致，绝大多数情况相同，但理论上存在错位的可能。
2. **假设放置目标永远是石头**：真实星球的洞穴/空气会让部分列放不下矿，因此虚拟产量**略高于**实地同区块的可采量。
3. **era>0 的重置矿脉**：把 oreveinSeed 先过 FNV 哈希再混入 era，生成「分布规律与真实星球一致」的新矿脉，但内容与真实地形无对应关系（这是设计而非复现）。
4. **星球图标**：按星球名的哈希从 64 格图集里取一格，整合包里星球多于 64 颗时会有两颗共用一张图（纯装饰，不影响数据）。

## 技术说明

- **服务端权威**：全部模拟、资源扣取、产物缓冲都在服务端 `checkProcessing` 里推进（20t 批次），客户端只通过 `StringSyncValue` 编码串拿展示数据（`\u001F`/`\u001E` 分隔，本地化全在客户端做）。
- **GUI 不读客户端的星球表**：MUI2 两侧各建一棵控件树、只按名字同步 sync 值。专用服务器的客户端，本地矿脉/油田配置未必与服务端一致，所以星球页是固定 5 行的「行池」，每行有没有星球、显示什么全由 `scPlanets` 同步串决定（`PlanetRowWidget` 没数据就整行不画）。选中态是服务端星球表的下标，表本身按「火箭等级 → 维度名」排序。
- **尺寸链**：面板宽 235、终端行宽 = 面板宽 − 8、终端行高 128、面板高 = 4 + 128 + 22 + 76 + 4 = 234。只改面板宽不改终端行宽，内容会画到终端外面。
- **星球种子捕获**：`PlanetSeeds` 挂 `WorldEvent.Load` 抓各维度 seed，存主世界 `WorldSavedData`；`PlanetRegistry` 惰性构建星球表（GC 天体 × GT 矿脉 × GT 油田，无矿无油的剔除，主世界剔除）。
- **结构定义**：形状、字符含义与装配都在 `SpaceCenterStructure`：装配时先收集形状里的全部字符再逐个登记，出现没登记的字符当场报出是哪个。StructureLib 要求形状里的每个字符都有元素绑定，漏一个 `build()` 就抛异常，而这个构建是惰性的——编译、注册、服务端冒烟都碰不到，要到成型检查或 NEI 的多方块预览才炸。
- **状态机与宿主的接缝**：`SpaceCenterMiner` / `SpaceCenterDriller` 只依赖 `MachineHost` 接口与 NBT，材料对它们是不透明句柄；`MTESpaceMiningCenter` 实现该接口，负责 GT 世界生成与输入仓。矿石列表由宿主按材料 id 排好序再交给状态机。
- **贴图**：全部由 `tools/GenSpaceCenterTextures.java` 程序化生成（`java tools/GenSpaceCenterTextures.java`，生成后读回自检）。全息核心与天线是竖条帧图集 + `.mcmeta`：中间 8 列是带下扫扫描线的能量柱，天线图集里基座 / 桅杆 / 发射头各占一块，`SpaceCenterPartRenderer` 按固定的像素区域取图。星球图集 16 列 × 4 行、每格 32×32、透明底。
- **动画与性能**：区块几何（能量柱、相邻核心之间的横梁、天线三段造型）是静态的，走 ISBRH 烘焙进显示列表；扫描线 / 呼吸灯是贴图帧动画。逐帧的部分全在 `RenderWorldLastEvent`（`SpaceCenterEffects`）：星环每一段都是朝向相机的缎带，动感的来源是亮度沿轨道流动（均匀的环绕自己的轴转看不出来）；天线束与投影锥只在机器运行时画；星环与全息星球 64 格内画、天线束 128 格内画。锚点不靠同步——客户端没有成型的层数与朝向——而是每 20 tick 摸一遍世界：背向判定在 `SpaceCenterGeometry`（两端共用的纯逻辑，回归检查拿真实形状核对过）。2.1.0 曾把锚点钉在控制器正上方，而控制器在前缘、中心列在它后面 3 格，特效于是全部失踪。
- **全息星球的同步**：服务端把图标槽位（7 位）放进控制器的 `getUpdateData`，变化时发 `CHANGE_CUSTOM_DATA` 块事件；客户端在 `onValueUpdate` 里收，不需要星球名也不需要星球表。
- **Galacticraft 隔离**：`GcCompat` 是唯一的 GC 类型引用点（`ItemTier(\d+)Rocket` 类名识别火箭等级）。门在 `SpaceCenterRegistration.isGalacticraftPresent()`，**必须在一个不引用 GC 类型的类里**——`GcCompat` 里有把 `Planet` 传给形参 `CelestialBody` 的方法，GC 缺席时 JVM 校验就会抛 `NoClassDefFoundError`，门放在它自己里面会先炸。
- **回归检查**：`gradlew verifySpaceCenterMachines`（已挂进 `check`）用内存假宿主驱动两个状态机与层数判定：下潜 / 开采 / 缺料暂停 / 读档续挖 / 纪元重置 / 区域推进 / 流体口径 / 数值口径 / 2..9 层与残缺结构；另外拿真实的 StructureLib 把结构定义完整装配一遍（形状里每个字符都要有元素——2.1.0 漏了表示空气的 `.`，成型检查和 NEI 多方块预览一碰就崩），拿真实形状搭出四个朝向 × 两种高度 ×「底座边缘摆桁架/摆仓」的内存网格核对特效锚点扫描（背向、中心列、顶盖、全息核心与天线的数量和位置），并校验中英文词条的占位符数量与传参一致（2.1.0 的钻机词条占位符 5 个、传参只给 4 个，悬停即崩），共 358 项断言。两类新检查都做过变异验证：把 2.1.0 的锚点 bug 或少传参引回去，断言当场变红。
