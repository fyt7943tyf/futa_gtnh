# 2.0.4 改动与交付说明

## GT 存储输入总线：抽取不足时输出逐槽位诊断

2.0.2 起，存储输入总线在真实抽取不足时只输出一行汇总（计划抽取、实际抽到、能为计划量付出的能量），看不出是哪种物品、哪个槽位。线上日志显示两次抽取不足都发生在能量充足时，只少抽了一点，原因需要更细的数据。

本次在抽取不足的路径上追加每个相关槽位一行日志：

```
Stocking bus dim 0 (x, y, z) slot item=<物品ID>@<损坏值>[+nbt] simulatedAtCheck=<检查时模拟的数量> consumed=<本次消耗> pulled=<实际抽到> simulatedNow=<失败后再模拟的数量> networkListNow=<终端列表里的数量>
```

读法：

- `simulatedNow` 明显大于 `networkListNow`：某个来源被多条路径重复计数，查这台总线所在网络里通向同一来源的 storage bus 和接口。
- `simulatedNow` 与 `networkListNow` 接近且都小于 `consumed`：网络里确实只有这么多，说明检查当时的模拟数据是过期的（库存刚变化、区块刚加载），而不是重复计数。
- `networkListNow=-1`：该网络没有返回库存列表，只有模拟数据可参考。

失败后的数字是在退回物品之后取的，此时网络已回到检查开始时的状态，几个数字可以直接比较。诊断只在抽取失败时执行，每台总线 5 秒内最多一次；诊断本身出错只记一行警告，不影响机器和退回。保护逻辑（按能量限量、检查内退回、被 ProgrammableHatches 改过抽取来源的总线跳过、`-Dfutagtnh.stockingBusGuard=false` 关闭）与 2.0.2 相同。

## 验证与兼容

- `gradlew.bat --offline build spotlessCheck`：完整构建、格式及既有回归检查。
- `verifyStockingBusGuard` 20 项检查通过，其中短抽取场景会实际输出逐槽位日志（含前一个槽位抽取成功、后一个槽位不足的情形）。
- 已在本地实例上测试。

没有新增网络协议、NBT 字段或配置项，仅服务端生效。
