# 公共 ME 网络：旧共享库存的接管与恢复

这次迁移把共享背包的存取入口交给真实 AE 网络。原有全服公共仓库继续使用同一份库存文件，作为公共 ME 网络的一种存储介质；迁移本身不把物品搬进新磁盘，也不从外部箱子抽取物品。

## 首次启动的处理顺序

服务端在向玩家、机器和 ME 网络发布仓库之前调用 `SharedStorageFile.loadForAe(worldDirectory)`：

1. 沿用已有读取规则验证主库存文件；主档不可读时尝试常规 `.bak`。遇到过新的库存格式时直接停止，不回退到旧备份。
2. 把实际成功读取的原始文件复制为专用迁移备份，校验 SHA-256。这个备份使用新建语义，绝不覆盖或轮换已有文件。
3. 写入迁移标记的临时文件，刷出文件内容后，以原子重命名提交标记。文件系统不支持原子重命名时，迁移停止；不会改用非原子提交。
4. 提交完成后，运行时接管这份原有库存。只有此时才能发布可用仓库。

新世界也先建立空库存文件，再生成备份和标记，因此在第一个玩家存物品前重启仍可恢复同一个仓库身份。

## 文件和版本

文件位于主世界存档的 `data/` 目录：

| 文件 | 用途 |
| --- | --- |
| `futa_gtnh_shared.dat` | 正在使用的内部库存、限额、未知条目与未决合成托管 |
| `futa_gtnh_shared.dat.bak` | 原有普通保存流程维护的上一版库存备份 |
| `futa_gtnh_shared.dat.pre-ae-v1` | 首次认领前的专用原始备份；后续保存不会覆盖它 |
| `futa_gtnh_shared.dat.ae-migration` | 已提交的迁移元数据 |
| `futa_gtnh_shared.dat.ae-migration.tmp` | 迁移提交前的临时标记；不是生效状态 |

迁移元数据使用压缩 NBT，当前迁移版本为 `1`，记录后端 `ae-shared-pool`、稳定的仓库 UUID、迁移备份的 SHA-256，以及实际读取来源是主档还是常规备份。运行时通过 `getAeStorageId` 读取稳定标识，不把临时 AE 网对象的身份当作永久仓库 ID。

迁移版本与原库存格式版本分开。认领时保留原 `.dat` 的完整字节，库存格式仍按现有 `SharedStorage` 读写规则处理；不会为了认领改写物品数量或清理未知字段。后续普通保存继续保留无法解析的物品、流体和合成托管条目。

## 三类库存必须分开核对

| 类型 | 迁移处理 |
| --- | --- |
| 内部池 `items` / `fluids` | 原地接管，数量继续使用 `long`；不按当前限额截断旧库存 |
| 旧存储总线连接的箱子、抽屉、储罐 | 实物留在原容器，由 ME 存储提供者发布；不复制进内部池 |
| `craftingItems` / `craftingFluids` 未决托管 | 保留原状态，不自动返还为可用库存 |

共享终端的展示快照可能包含外部容器，所以不能把终端显示的总量重新导入内部池。外部同一个容器被多面总线连接时，按目标容器、物品或流体键取最大可见数量，仅发布一份库存。

未决托管表示 AE 投递或 IO 搬运调用结果尚未确认，来源容器、接收设备或 CPU 可能仍然持有这些货。盲目回库会造成复制。迁移不会自动判断或退款；原有 `/futashared escrow` 核对和管理员恢复流程继续保留。恢复前先暂停相关 IO，核对来源、目标和 CPU；不能把所有托管都当作未被接收的库存。

正常 IO 返回的未接受余量直接回到内部池；AE 或第三方容器抛出异常、结果无法确认时，该原料保留为不可用托管并暂停继续搬运，避免自动重试造成复制。托管随正常仓库保存持久化，不是每次 IO 都强制刷盘，也不提供跨 Minecraft 区块、玩家、CPU 存档的崩溃事务。

主动 IO 也复用这些托管字段：当 AE 注入、提取或目标容器回调抛异常，无法确认对方是否已经收货时，该原料会停止自动重试，待核对来源、目标与 CPU 后处理。已知未被接受的余量只回到内部池，不再经过一次 ME 注入；内部池回收容量不足时，剩余数量继续保留在托管中。托管记录与普通库存一样标记脏状态并按已有保存周期写盘，不会每次搬运同步刷盘，也不构成共享文件、AE CPU 与 Minecraft 区块文件之间的事务。

## AE 流体 NBT 兼容

项目固定的 AE2 rv3-beta-1082-GTNH 在创建 `AEFluidStack` 时未复制 Forge 流体的 NBT，原有 `setTagCompound` 也是空实现。直接转换会把同种流体的不同标签合并。本模组补齐这两个入口和精确类型比较，复用 AE 自身的 NBT 规范化机制；副本、网络包和存档继续走原生 AE 路径。旧池中的带 NBT 流体保持各自身份和数量，不能将它们去标签后导入。客户端和服务端须一并更新，否则旧客户端仍不能正确识别这些变种。

## 中断、损坏和重启

- 只有专用备份、没有已提交标记：普通加载和保存拒绝继续。启动迁移可以续接，但必须确认当前权威库存文件与该备份逐字节一致；不一致时停止，保留两份文件供人工核对。
- 标记已经提交：重启读取当前主档或常规备份，复用同一个 UUID；不会再次复制或累加迁移前库存。
- 标记损坏、版本未知、UUID 不合法、专用备份缺失，或启动校验发现 SHA-256 不符：停止接管，不退回到可写的旧模式。
- 迁移后主档和常规备份都不存在：停止加载，不能把迁移前专用备份自动恢复为当前库存。迁移之后可能已有玩家领料或机器消耗，直接回放旧快照会重新产生这些物品。
- 主档损坏但常规备份可读：继续沿用原有恢复规则；迁移备份记录实际读到的常规备份，并保留损坏主档现场。

普通保存检查迁移标记的格式、身份与所需文件是否存在；启动和重新加载还会校验专用备份的完整 SHA-256。迁移错误必须让启动或重载失败，不能捕获错误后改用一个空仓库继续服务。

不要通过删除迁移标记来“重试导入”。也不要在服务端运行时单独替换旧库存文件。需要回滚时应停服，恢复同一时刻的完整世界备份，包括库存文件、迁移元数据、AE 元件和 CPU、机器及玩家数据；只回滚共享池无法保证物品守恒。

## 旧设备的兼容边界

旧共享终端、快捷键和自动化入口通过公共 ME 存取路径访问仓库。旧存储总线由 `LegacyMeBusProvider` 作为原生 AE 存储提供者注册，每条总线保留优先级、读写模式和筛选。

总线模拟存取只做预检，物品不调用写槽或扣槽方法，流体使用 Forge 的 `fill(..., false)` / `drain(..., false)`。真实存取按容器实际接受或取出的数量结算，允许部分成功。Storage Drawers 使用物理数量和容量进行模拟，不把虚拟输入输出窗口的数量当成总库存。

目标区块未加载、目标失效、配置已变化的旧句柄不能继续存取。同一公共 ME 网的 AE 主机、共享终端、IO 节点和其他共享总线不作为外部存储目标，避免把公共网络再次包回自身。主动 IO 的排除目标和“只进内部池”上下文会传递给存储提供者，避免输出后立即回抽或输入后写回源容器。

原生 AE 监视器已经记录的总线存取不再次发布库存增量；外部容器变化和总线拓扑、配置变化由后续 ME 存储更新处理。服务端停止、世界切换或公共网失效时，提供者应从旧网注销，并在新网有效后重新注册。

## 旧存档验收建议

先复制完整世界作为验收存档，记录内部池、外部容器和未决托管的独立清单。至少选择普通物品、带 NBT 的工具或元件、大于 `Integer.MAX_VALUE` 的数量、带 NBT 的流体、未知模组条目，以及超出当前自动化限额的旧库存。

首次启动后核对原主档与专用迁移备份的哈希、稳定仓库 UUID 和各类数量。对同一容器的多面总线、只读和只写总线、筛选、优先级逐项确认；旧终端与 AE 终端应该查询同一个公共网。

实际存取一批物品和流体后正常停服重启，再核对当前库存。专用备份仍应保持首次认领前的字节，UUID 不变，已取走的库存不应恢复。另在独立副本中验证缺失标记、损坏标记、中断提交、常规备份恢复，以及迁移后当前库存全失的停止行为。

仓库中的 `verifySharedStorageReadApi` 包含真实文件的迁移回归；`verifyStorageBus` 包含真实生产存储提供者、存取模拟、去重、通知和容器数量检查。这些检查不替代 GTNH 客户端与独立服务端的实际接入、区块卸载、合成 CPU 和重启联调；实际执行结果应以本次构建日志为准。
