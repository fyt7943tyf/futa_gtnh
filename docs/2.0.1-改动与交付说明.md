# 2.0.1 改动与交付说明

## 修复 GT 存储输入总线抽取不足时丢料关机

GT5U 的 ME 存储输入总线（Stocking Input Bus）在配方检查时先用**模拟**抽取算出网络里有多少料，配方匹配并扣减后，再在同一 tick 对网络做**真实**抽取。真实抽取量与消耗量不符时，总线报 `stocking_bus_fail_extraction`、机器停机，已经抽出的材料不会退回，配方也没有开始，材料就这样消失（上游 GTNH 议题 #25875，至今未修）。

模拟抽取完全不看 AE 能量，而真实抽取按 `Platform.poweredExtraction` 先付能量、能量不足就只抽能量够的那部分。能量缓存小的独立子网（能量接收器、控制器内部缓冲都只有 8000 AE）一次要抽的量超过当前储能时，必然少抽；主网通常有大量储能，所以同一个总线代码在不同网络里表现不同。

本次在 FutaGTNH 里用 Mixin 做三件事（`MixinGtStockingBus`、`MixinGtMultiBlockRecipeCheck`，辅助代码 `StockingBusGuard`）：

1. **按能量限量**：每次配方检查开始时探测一次网络当前能付得起的物品数，模拟抽取得到的数量超过它就截到该值；一件也付不起时视为没有这种物品。机器只会看到真正抽得出来的量，原来的"丢料关机"变成"本轮料不足、等下一次检查"。
2. **丢料时退回**：如果真实抽取仍然不足，把这次已经抽出的物品（包含前面抽取成功的槽位）原样注回网络，机器照常报错停机，但材料不再消失。仅在 `MTEMultiBlockBase.checkRecipe()` 内退回——此时配方确实没有开始。烧燃料类机器在运行中也会调用同一对钩子，那里不退回，避免已经产出后又退料造成复制。
3. **日志**：每次抽取不足时在服务端日志里输出一行（每台总线 5 秒内最多一次）：总线坐标、物品、需要量、实际抽到量、当时网络能为该请求付出的能量；退回时再输出退回数量。有了这几个数字就能区分"能量不足"和"同一来源被多条 storage bus 重复计数"（后者模拟量会虚高，能量够但仍抽不到）。

JVM 参数 `-Dfutagtnh.stockingBusGuard=false` 可关闭限量和退回，日志保留。

## 验证与兼容

- `gradlew.bat --offline build spotlessCheck`：完整构建、格式及既有回归检查。
- 新增 `verifyStockingBusGuard`（已并入 `check`）：用真实 Mixin 变换 GT 的总线和多方块基类，再用假的 AE 网络驱动变换后的代码，共 16 项检查：钩子都已应用；能量 50 / 充足 / 0 时模拟量分别被截到 50 / 不变 / 清空；精确抽取不退回；检查内短抽退回 30 件；检查外短抽不退回；第二个槽位不足时前一个槽位和不足的部分一并退回。
- Mixin 目标签名核对过：GT5U 5.09.54.175（编译基线）、5.09.54.265（测试服）、5.09.55.2（整合包 daily 823，含 Java 17 版类）三者的 `MTEHatchInputBusME`、`MTEMultiBlockBase.checkRecipe()` 和 AE 的 `Platform.poweredExtraction` 描述符一致。

没有新增网络协议、NBT 字段或配置项。仅服务端生效，客户端无需更新。后续升级 GT5U 或 AE2 时，若上述方法签名变化，Mixin 会在启动日志里报告应用失败，不会静默失效。

**尚未在真实服务器验证**：能量不足只是目前在源码中确认的、不需要多路径也能触发的成因。更新后请留意日志里 `Stocking bus short pull` 的 `powerAvailableForRequest` 是否小于 `needs`：小于说明是能量问题（限量应已消除停机）；够用却仍然抽不到，则是重复计数或其他成因，凭这些日志继续排查。给子网接石英纤维连主网可以让它借用主网储能，同样能缓解能量不足。
