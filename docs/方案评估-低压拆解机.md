# 低压拆解机方案评估

日期：2026-10-02。本文保留设计评估；实现已随 1.23.0 加入，实际行为见 [README-拆解机.md](../README-拆解机.md)。用户最终确定配方统一 40 tick（2 秒）。

## 结论和确定需求

可以在 futa_gtnh 中新增独立的 GT 单方块拆解机。现有项目已经硬依赖 GregTech，具备物品和流体身份键、网络及界面基础；新增功能不需要引入 GTNN 或 Kotlin。

用户已经确定：机器在 LV 阶段可以制作、成本较低；全部拆解配方使用 LV 1A；输出物品槽和流体槽必须容纳完整的一次拆解产物。

建议具体解释为：只有一个 LV 机器等级；每 tick 消耗 32 EU；不继承原合成配方的电压，不因原配方是 HV/IV 等级而拒绝拆解；一次执行一个拆解批次，不并行、不超频。消耗 1A 与最大输入电流是两个参数，如希望电气输入也严格为 1A，需要同时实现 maxAmperesIn() = 1。不能只设置 RecipeMap.amperage(1)：GT 普通机器的输入电流上限有自己的计算逻辑。

## 当前项目与 API 的核对结果

- dependencies.gradle 使用 GT5-Unofficial 5.09.54.175；GTNH 2.9.0 RC1 官方清单使用 5.09.54.183。实现必须分别核对和验证，不能以 master 的接口代替这两个版本。
- FutaGtnhMod.java 已有 FMLLoadCompleteEvent 钩子，CommonProxy.java 已有公共注册生命周期。
- 现有代码未找到自定义 GT MetaTileEntity 注册。拆解机将是项目首次接入这一类机器，需要处理稳定 MTE ID、实例复制、纹理、存档及客户端界面。
- ItemKey 和 FluidKey 包含元数据/NBT，适合合并产物和索引配方；只复用身份表示，不把机器产物直接写入全服共享仓库。
- GT 的 MTEBasicMachineWithRecipe 底层只有一个 mOutputFluid 和一个输出罐；扩大 RecipeMap.maxIO 的流体输出数量不会自动提供多个真实罐。
- GT 普通机器有将待输出物品数量截到 64 的代码，不能直接把原材料的大堆叠数量送入继承的结算流程。
- 当前 assemblerRecipes 的接口上限是 9 个物品输入、1 个流体输入；真实装配线配方独立保存在 GTRecipe.RecipeAssemblyLine.sAssemblylineRecipes，展示表上限为 16 个物品输入、4 个流体输入。不能用 NEI 的假配方作为全部真实生产数据。

## 推荐的机器参数

| 参数 | 建议值或行为 |
| --- | --- |
| 等级 | LV，单方块 |
| 工作功率 | 32 EU/t，固定 |
| 输入电压/电流 | 最大 32 V、1A；使用 GT 电网 |
| 输入 | 一个成品输入槽，按拆解批次消耗 |
| 物品输出 | 最少 36 个真实槽，必要时按配方目录扩大 |
| 流体输出 | 最少 8 个独立罐，必要时按配方目录扩大 |
| 每罐容量 | 至少 64,000 mB，且不低于目录中一次批次所需容量 |
| 时长 | 用户最终确定统一 40 tick（2 秒） |
| 储电 | 暂建议 32,768 EU，用于稳定供电；不改变 32 EU/t 消耗 |
| 自动化 | 侧面输入成品、背面物品/流体输出；GUI 允许分别选择待抽取的流体 |
| 缺电/输出堵塞 | 暂停或等待，保存任务，不删除输入和产物 |

便宜合成建议：一个 LV 机器外壳、一个 LV 电路、一个 LV 电动马达、一个 LV 电动活塞、两条单股锡电缆、三块钢板。只使用 LV 可获得的材料，不要求机械臂、传感器或 MV 元件。以工作台配方注册即可，不要求额外生产机器。最终材料对应的物品名以依赖版本实物为准。

36 槽和 8 罐只是建议下限，并不是对所有附加模组配方的容量证明。生成目录后计算最终容量，不能用固定的 9 槽/1 罐，或默默截断溢出产物来满足要求。

## 实现路线

建议继承 MTETieredMachineBlock，复用 GT 的方块、电网、方向和覆盖板基础；自行实现处理状态机、物品输出、多个流体罐和 ModularUI 2 界面。MTE ID 使用配置中的稳定值，注册前检查冲突；发生冲突清楚报错，不能每次启动随机选 ID 导致存档指向别的机器。

不建议直接继承 GTNN 的 MTEDisassembler，也不建议在 MTEBasicMachineWithRecipe 上同时替换其单流体结算、持久化、GUI、输出检查和自动输出。后一条路线看似改动少，实际上很容易遗漏父类行为。

建议新增 disassembler 包，内部划分：

- DisassemblerRegistration：机器和合成配方注册、ID 检查。
- MTELVDisassembler：GT 机器实例、电力、状态和存档。
- DisassemblyCatalog / DisassemblyRecipe：不可变配方目录和成品索引。
- CraftingRecipeAdapter / AssemblerRecipeAdapter / AssemblyLineRecipeAdapter：读取不同来源并转成统一的材料清单。
- DisassemblyOutputPlan：合并、分堆、流体装罐模拟和容量计算。
- DisassemblerGui / 配方展示适配器：分页物品槽、流体槽、状态及 NEI 展示。

预注册机器与图标；在 loadComplete 阶段读取生产配方，形成不可变目录并确定容量规格；世界加载后创建的真实实例使用完成的规格。原型、真实实例、旧存档、客户端同步必须采用同一槽位编号规则，不能仅扩大 GUI 而不扩大后端库存。升级后保存过的槽位不得缩小或重排。若有其他模组在更晚的 loadComplete 回调修改配方，需要调整排序或提供显式重建机制；不在每个 tick 扫描全表。

## 配方覆盖与返还规则

首版建议支持：可静态解析的普通/矿辞/GT 有序和无序工作台配方、GT 组装机配方、真实装配线配方。电路组装机及其他专用生产配方作为独立适配器，可在规则一致后加入。

“所有拆解配方均为 LV”是对拆解功率的要求，不等于所有加工机器的配方都应倒转。烧炼、化学反应、矿物处理、发电、配方展示占位符不应被当作制作配方自动加入。

优先读取 CraftingManager 中已注册的最终工作台配方，解析明确支持的配方类型，避免照搬 GTNN 在私有构造调用上捕获配方的 Mixin。特殊配方如果依赖玩家、世界、动态 NBT 或自定义匹配逻辑，不能当普通静态配方反转，需要单独适配。

统一材料清单应包含：成品的物品身份、消耗批次数量、物品产物及数量、流体产物及 mB、配方来源、固定功率和处理时间。材料数量计算用 long 并检查溢出，创建 ItemStack/FluidStack 时按 API 的 int 限制安全转换。

返还真实消耗的物品和流体，不复制 GTNN 的整套磁化材料降级、电路替换逻辑。零数量的程序电路、模具、催化剂等非消耗输入不应成为拆解产物。工作台工具及合成后原本返还的容器必须按净消耗处理；复杂容器配方暂不自动反转。研究物品、数据棒、洁净室等运行条件不属于消耗材料。

如果一份原配方产出 4 个成品、消耗 1 个零件和 144 mB 流体，则反向批次先定义为“4 个成品 → 1 个零件 + 144 mB 流体”。只有所有物品数量、流体数量均能整除时才缩小批次。不能把零件数量向上取整，或每拆一个成品返还一整份原材料。输入槽必须能放下批次；超出普通堆叠上限的来源需要专门的批量输入适配，不能假装已支持。

同一成品可能存在多条成本不同的合成路径。物品没有制作历史，无法准确判断当初使用了哪条路径。不能让玩家任意选择返还昂贵配方，也不能把“第一条配方”或一个无依据的成本排序当成安全答案。建议默认规则：

1. 按成品身份和批次数量规范化候选，统计所有已支持制作路径。
2. 材料清单相同的候选合并。
3. 单一明确清单可以完整返还；冲突清单先按明确手工覆盖解决。
4. 未解决冲突默认不生成，并在报告中列明原因；可选的保守返还模式只返还各路径共同消耗材料的最低数量，且在 NEI 中明确展示。

即使这样也不能声称绝对杜绝材料循环：未适配的其他模组来源、矿辞替代品及特殊配方可能提供更便宜路径。按成品聚合冲突、覆盖规则和循环样例验证是必要工作。用户若希望开放回收效率，可通过明确配置改变该策略。

带物品库存、能量、流体或配方之外 NBT 的成品需专门判断：与普通成品配方匹配时不得忽略这些状态并吞掉内容。默认拒绝无法证明为空/可安全处理的物品，允许已适配的空机器、已定义配方的带 NBT 物品。

## 输出容量与一次结算

对每个允许拆解的批次，先按物品身份（含 NBT）合并数量，再按每种物品的实际最大堆叠数量分堆：

`所需物品槽 = sum(ceil(该物品数量 / 该物品堆叠上限))`

不能一律假定每槽 64；不可堆叠物品及堆叠上限为 16 的物品同样要正确处理。

流体按流体身份（含 NBT）合并：需要足够的独立罐数容纳不同种类，并按一次批次的总量确定每罐容量。如果一个流体的返还总量超过罐的 int 容量上限，需分罐或使用独立的大数量后端；首版必须显式处理这一边界。

最终容量至少满足全目录最坏批次。建议最小 36 物品槽、8 流体罐、每罐 64,000 mB，生成后扩至计算所需的数量/容量，GUI 分页显示。实际最大值要通过运行目标整合包的配方扫描报告得到；本次评估没有运行该扫描，不能把建议下限写成已验证的最大值。

开工前同时模拟现有物品输出槽和流体罐。只有完整批次都能放下才接收输入。处理期间保存输入与完整产物计划，预留容量；或在完成时重新检查全部容量并等待。物品输出槽与流体输出罐只能抽取，不能由玩家或管道写入；若支持未来的额外写入操作，也必须服从容量预留。

完成时在服务端同一个操作中提交全部物品和流体，不能先输出物品、再因流体装不下而重试整批。缺电、卸载和重启要保留任务；机器被拆除时只返还被保存的未完成输入，不能同时返还输入和尚未完成的材料。运行中的产物清单应随任务存档，升级配方后不要重新计算旧任务产物。

多罐向管道的 drain(指定流体) 应能遍历全部罐；不指定流体的 drain 使用稳定顺序和轮询，避免第一罐长期占用使后面的流体无法导出。GUI 手动导出、GT 管道、AE 接口和相邻共享终端抽取要使用相同的后端，不形成各自独立副本。

## 验证与工作量

实现工作量为中等偏大。便宜合成和固定 LV 耗电比较简单；主要成本在多罐机器、容量模拟与持久化、不同制作路径的冲突处理，以及配方查看器展示。无需移植 GTNN 的其余回滚模块。

先实现纯数据目录和生成报告，再实现机器及存档，最后接入 GUI、管道和 NEI。报告应包含按来源的候选/成功/跳过数量、冲突成品、最大物品槽需求、最大流体种类和每批次流体量。

必要验证：

- LV 材料能制作机器，32 V 1A 能稳定工作；每个工作 tick 扣 32 EU，原配方等级不影响拆解电压。
- 超过 9 种物品、多种流体、堆叠超过 64、不可堆叠物品均完整输出。
- 物品已满、一个流体罐已满或罐中类型冲突时不消耗新输入，不截断材料。
- 断电、暂停、区块卸载、保存重启、拆机时没有双份输出或输入丢失。
- 不同配方路径、批量产出、零数量催化剂、容器返还及动态 NBT 不产生明显循环。
- 指定流体和普通 drain、漏斗、GT 管道、AE/共享终端抽取能访问全部实际输出。
- NBT 库存和任务在客户端、服务端一致；GUI 换页不复制或丢弃材料。
- 按仓库要求运行 build 和 spotlessCheck，并在目标 2.9.0 客户端/服务端实测。

评估阶段只检查了源码、项目结构及本地依赖 jar 的接口。1.23.0 的构建和回归检查结果记录在发布变更文档中；开发环境启动检查不替代完整 2.9.0 整合包实测。
