# 1.34.1 共享存储切换原生 AE 后的性能对比

这是优化前的历史测量。增量索引的最终同进程四组对比见 [1.34.2 报告](1.34.2-原生存储索引优化性能对比.md)。当前基准工具已扩为四组，并使用真实 `ApiStorage`；不要将当前命令的绝对值与本文旧测试适配环境逐项混比，原始历史 JSON 继续保留。

测量日期：2026-10-27。对比旧共享池、当前公共 AE、直接挂载原生元件的普通 AE。测试使用隔离数据及 `build/` 下的文件，不读取或修改生产服务器。

当前实现的额外成本集中在搬运后的索引维护，特别是空库存请求、后部元件命中和兼容直写路径。全量枚举、保存压缩与普通 AE 接近；旧共享池的哈希表搬运成本较低。下表分别呈现常规物资和 NBT 密集物资，不能将一个场景的倍率推广到全部操作。

## 三组实现与公平性

| 组别 | 实际使用的实现 |
| --- | --- |
| 旧共享池 | `v1.33.10` / `e0f2358e6e8f5804a389a7ffbe67592706a0a010` 的完整 `SharedStorage` 冻结副本，以及该版本 `ItemPool` / `FluidPool` 的原方法体 |
| 当前公共 AE | `v1.34.1` 的 `NativeMeCellArray`、真实 `CellInventory`、限额/发布包装层、位置索引及自动扩容入口 |
| 普通 AE | 相同的 AE2 / AE2FC Universe 元件，经真实 `CellInventory.getCell` 直接挂入库存处理器；没有公共阵列包装层与分配器 |

三组均经过相同的真实 `NetworkMonitor` / `NetworkInventoryHandler`，使用相同资源、数量、请求顺序和元件类型。4096 种物品加 4096 种流体时，两个原生组均有 132 枚元件，单枚最多 63 种资源。普通 AE 组的保存回调只设置脏标记；公共组使用实际 `WorldSavedData` 脏标记。旧提供者固定为已接入状态，排除无关的全局网络身份查询。

测试不把新实现与普通 1k/64k 盘混比容量、盘数和类型限制；普通 AE 列表示相同原生媒体的标准库存路径。新类型的在线扩容/拓扑重建没有单独给出稳定延迟分布；迁移阶段的媒体分配在实测范围内。

## 环境与采样

- Apple M1 Pro，10 个可用处理器，macOS aarch64，OpenJDK 17.0.20.1+1-LTS，最大堆 2048 MiB。
- AE2 `rv3-beta-1082-GTNH`，AE2FC `1.5.108-gtnh`；三组均在加载当前 Futa Mixin 的同一 JVM 中运行。
- `plain`：不带 NBT 的元数据物品变体，以及分别注册的独立流体；每通道 63 / 4096 种。
- `nbt`：同一基础物品/流体的不同完整 NBT 变体；每通道 1 / 63 / 1024 / 4096 种。单类型夹具无 NBT。
- 每种资源均为 1000000 件或 mB。数量按 `long` 存取，不逐个遍历库存单位。
- 每个负载运行 3 个独立 JVM。常规操作每组预热 300 个批次、采样 600 个批次；组别顺序交错轮换。快速查询每批 16/64 次、模拟每批 8 次，结果除以批次大小。
- 序列化/加载各预热 12 次、采样 50 次；兼容直写各预热 30 次、采样 60 次。迁移及校验启动每个进程各测一次。
- 表中 P50 是 3 个进程 P50 的中位数，分配量是 3 个进程每操作平均分配量的中位数；不是把所有样本混合后计算的百分位。原始 JSON 同时包含各进程 P95/P99/最大值和 GC 次数。
- 一次“取出并放回”是 2 次实际存取；“物品+流体各取出并放回”共 4 次。缓存查询行使用预建 AE 请求，不含共享 API 入口的原型/NBT 转换。

## 已定位的热点及改造方向

这些解释结合三组耗时、分配量和实际循环结构；本次没有提供采样 profiler 的 CPU 百分比分摊。

1. `NativeMeCellArray.Channel.Slot.limited.extractItems` 在实际请求返回空值时仍调用 `reindex`。查找不存在的资源会经过多个元件，导致每枚元件的全部资源键重新构造。应先跳过无实际变更的请求。
2. 正常数量变化也重建整枚元件的成员索引，包含键和 NBT 拷贝。位置索引只需要跟踪某种资源是否出现/消失；数量继续从原生 AE 读取，可按受影响键增量更新。
3. `Channel.insert` 在兼容直写、迁移和扩容路径中对所有元件重新索引。应仅处理实际变化的元件，并对迁移批量装入后统一建索引。这也能保留 AE 作为唯一数量权威。
4. 存储内容查询及完整枚举接近普通 AE，优化应优先处理上述搬运/索引路径。保存压缩本身与普通 AE 接近；不能将全部新增成本归到随身终端或跨维度逻辑。

源码位置：[元件包装层](../src/main/java/com/futa_gtnh/me/NativeMeCellArray.java)、[阵列插入与索引](../src/main/java/com/futa_gtnh/me/NativeMeCellArray.java)。本轮仅增加测试工具和报告，存储逻辑与库存格式没有修改。

## 正确性、复现及边界

- NBT 三轮各通过 212592 项断言；无 NBT 三轮各通过 170543 项断言，共 1149405 次断言。包含每项数量、NBT 身份、类型数、失败请求不产物资、模拟/真实请求序列结束后的总量核对及迁移后数量核对。

- 测量文件在独立的验证进程中重新解压，并由真实 AE/AE2FC 引擎重新挂载；逐键核对旧共享池、公共 AE、普通 AE 的完整库存及监视器缓存命中。
- 独立重挂载验证通过 NBT 31120 项、无 NBT 24962 项断言；完整 `./gradlew build spotlessCheck --offline --console=plain` 通过。发布 JAR 中确认没有冻结基线或基准类。
- 已补齐正常接入时的 `NetworkMonitor.forceUpdate`，并在测量前验证缓存中的每个条目。早期缺失首次刷新、读取空缓存的预跑不纳入本报告；本文只使用带 `monitorCachePrimedAndVerified=true` 的正式结果。
- 为脱离完整游戏启动，沿用仓库的测试注册表适配，提供空定义/比较注册表及真实 AE 列表工厂；存在适配入口调用成本。数量引擎、元件、库存处理器、监视器与序列化使用真实依赖实现。三组使用相同环境；绝对耗时不等同线上。
- 不含物理驱动器/线缆/机器 tick、能源和频道、玩家安全校验、在线监听器、客户端与网络传输、外接盘/存储总线、原料统计；这些路径的成本不能从表内数值反推。没有测常驻堆/RSS，也不是卸载 Futa 后整合包的 TPS 对比。
- 默认 NBT 夹具不是生产服资源分布；无 NBT 夹具也不包含全部 GT/第三方物品行为。两种数据共同说明本版本的索引维护热点，仍需结合实际生产服 profile 判断占比。
- 本次没有测接近 `Long.MAX_VALUE`、单种资源因数量容量而跨多盘的性能；当前夹具的元件数主要由 63 种类型限制决定。

```sh
# NBT：每通道 1/63/1024/4096 种；一个命令为一个独立 JVM
./gradlew benchmarkStorageBackends --offline --console=plain
# 无 NBT：每通道 63/4096 种
./gradlew benchmarkStorageBackends -PstorageProfile=plain -PstorageScales=63,4096 --offline --console=plain
# 对当前保存的基准文件逐键重挂载核对
./gradlew benchmarkStorageBackends -PstorageVerifySaved=true --offline --console=plain
./gradlew benchmarkStorageBackends -PstorageProfile=plain -PstorageScales=63,4096 -PstorageVerifySaved=true --offline --console=plain
```
